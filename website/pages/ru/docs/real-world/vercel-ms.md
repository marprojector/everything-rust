# vercel/ms

[vercel/ms](https://github.com/vercel/ms) (5.5k звёзд, коммит `4ff48ce`) превращает `"2 days"` в
миллисекунды и обратно; большинство проектов на Node подтягивают его через какую-нибудь зависимость. Портирован от начала до конца
с помощью everything-rust 1.5.1; крейт лежит в
[`demo/real-world/vercel-ms-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/vercel-ms-rs).

| Шаг | Результат |
| --- | --- |
| `analyze` | 1 модуль (`src/index.ts`), готов, готовность 96 |
| `bridge --kind napi` | `ms`, `parse`, `parseStrict` и `format` подключены через мост, ничего не оставлено на TS |
| `record --from-tests -- jest` | 975 кейсов: сгенерированные, ловушки и 340 вызовов, снятых с 167 тестов Jest в vercel/ms (первый порт использовал 149 входных данных, скопированных из них вручную) |
| порт | 200 строк на Rust вместо 184 на TS, включая `FormatIndex`, который читает `options` один раз на пакет |
| `diff` | 784/784 совпали на первой сборке; 975/975 со снятыми вызовами |
| `gate` | проходит (fmt, clippy, тесты, пути ошибок, размер, поведение) |
| `bench`, на вызов | 0.56x по записанным кейсам (поначалу 0.39x): `parse` на обычной строке занимает 79 ns, наравне с JS, но граничные случаи и выброшенные ошибки всё ещё стоят дороже через мост |
| пакет, `parse` x100,000 | JS 11.8 ms, Rust 0.65 ms: **18x**; 3.4x с учётом однократной передачи строк (2.1x до того, как строки стали передаваться склеенными) |
| пакет, `format` x100,000 | JS 2.1 ms, Rust 2.5 ms с учётом передачи: **0.8x** (поначалу 0.2x); `format(x, { long: true })` 1.2x |

Что порт должен был сделать правильно, всё это поймано записанными кейсами или ловушками:

- `/.../i` без флага `u` сворачивает регистр только ASCII-букв, тогда как `regex` в Rust сворачивает Unicode, поэтому
  `"1 ſ"` (длинная s) и знак Кельвина распознались бы как секунды. Порт сопоставляет единицы
  вручную, только ASCII.
- `Math.round` округляет половины вверх (`-2.5` даёт `-2`); `round` в Rust округляет от нуля.
- `${n}` печатает `1e+21`, `5e-324` и `0` для `-0`; порт воспроизводит преобразование чисел в строку из JS.
  В его первой версии также был баг с равенством (`25.728225708007812` печатался как `...813`), до которого
  целочисленный вывод ms никогда не доходит.
- `str.length` считает единицы UTF-16, поэтому ограничение в 100 символов считает эмодзи за два.

Найдено в инструменте и исправлено: пакетный метод napi со структурированным параметром (`options`
у `format`) не компилировался, так как сгенерированная привязка принимала `serde_json::Value`, который napi
не может преобразовать без своей фичи `serde-json`. Крейты с пакетными классами теперь включают её.

Что перенесено обратно в инструмент из этого порта:

- В сгенерированном `js.rs` есть `js::number_to_string` и `js::math_round`, проверенные против Node на
  20,000 случайных double; порт использует их вместо собственных копий. `number_to_string` берёт
  цифры из принтера serde_json: в 5x быстрее `format!` для целых, в 3x для дробных.
- Пакеты napi передают строковые элементы одной склеенной строкой со смещениями концов в UTF-16, числовые элементы
  одним `Float64Array`, а строковые результаты возвращают склеенными (`index.cjs` разделяет их через `slice`):
  в 2x быстрее для строк и в 20x для чисел, чем одно JS-значение на элемент. `new Batch(items)` и
  `run()` сохраняют свою форму.
- `analyze` отмечает `Math.round`, `toFixed` и регулярные выражения с `/i` без `u`, в которых упоминаются `s` или `k`,
  с рекомендациями по каждому.
- Вызовы стали дешевле: в napi каждая синхронная функция идёт через бинарный протокол без аргументов napi
  (аргумент стоит около 55 ns, весь вызов 22 ns), одна JS-обёртка на функцию вместо
  двух, параметры `serde_json::Value` передаются как значения с тегами любой формы, а ошибки возвращаются
  в буфере протокола. `parse` на вызов ускорился со 121 до 79 ns.
- `record --from-tests` заменяет ручное копирование тестовых входных данных: он записывает каждый вызов, который делает набор тестов,
  пока тесты выполняются, а код захвата исключается из покрытия (ms требует 100%).

Вердикт: `ms` это хороший порт и плохая цель для ускорения. Корректен на каждом записанном кейсе, быстрее
только когда программа разбирает много длительностей за раз.

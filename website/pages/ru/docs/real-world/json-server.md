# json-server

[json-server](https://github.com/typicode/json-server) (75k звёзд, MIT, коммит `89a34a4`,
1.0.0-beta.15) отдаёт REST API из JSON-файла: Node, tinyhttp и lowdb. Это первое целое
приложение, портированное от начала до конца по процессу для целых приложений (`app record`, `front-door`, `wire`, `lift`):
результат представляет собой один Rust-бинарник, который отвечает так же, как Node-сервер. Всё лежит в
[`demo/real-world/json-server-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/json-server-rs).

| Шаг | Результат |
| --- | --- |

| `app record --http` | 514 кейсов: 268 запросов, заданных через `--inputs` (каждый маршрут и метод, операторы where, сортировка, пагинация, embed, CORS preflight, статические файлы и диапазоны, 29 некорректных JSON-тел, `/__proto__` и другие имена прототипа, неверные экранирования) и 245 ловушек; каждый записан дважды, случайные идентификаторы оставлены как `[..]` |
| `front-door` | 513/514 при 99.8% фолбэка; промах это необработанный `ü` в URL, на который Node отвечает 400, а прокси перекодирует его |
| модули | `where-operators` 207, `parse-where` 289, `matches-where` 1,346, `paginate` 853 кейса (включая вызовы из собственных тестов json-server); `service` 461 и `app` 243 через два небольших адаптера, которые выполняют вызовы Service и настоящие HTTP-запросы; `gate` проходит на всех шести |
| `wire` | сначала чтения: 514/514 при 22.6% фолбэка, Node отвечает на записи, а Rust перечитывает файл, записанный Node; затем все маршруты: 514/514 при 0% |
| `lift` | бинарник на чистом Rust (5.3 MB), 514/514; командная строка `bin.ts` портирована вручную (справка, версия, проверки файла, баннер при запуске) |

После подъёма у модулей нет привязок, поэтому `tests/recorded.rs` каждого крейта воспроизводит его
записанные кейсы на порте: все 3,399 запускаются через `cargo test`.

Что порт должен был сделать правильно, всё это поймано записанными кейсами:

- Роутер tinyhttp не выполняет диспетчеризацию один раз: после каждого `next()` он снова сопоставляет все middleware и
  маршруты, по URL, который переписал последний middleware, и для `HEAD` выполняет каждый маршрут. Поэтому
  `HEAD /posts` выполняет обработчик GET, затем обработчик POST и отвечает 400 от POST; `//posts` пропускает заголовки CORS
  и парсер тела. Порт выполняет этот цикл как есть.
- milliparsec разбирает каждое тело POST, PUT, PATCH и DELETE как JSON, каким бы ни был его тип, а некорректное
  тело даёт 500 с сообщением V8: `Expected double-quoted property name in JSON at position 7
  (line 1 column 8)`, `Unexpected token 'x', ..."bbbbbbb": x}" is not valid JSON`. Порт
  воспроизводит ошибки парсера V8, включая позиции в единицах UTF-16; проверено против Node на
  3,806 некорректных входных данных.
- Сортировка использует `localeCompare` (ICU), реализованный через коллатор ICU4X и проверенный на 3,000 пар;
  `Number()`, `JSON.stringify` (`1e+21`, целочисленные ключи первыми), два парсера query-строк Node
  (которые декодируют `é%E9` иначе, чем WHATWG), dot-prop с его сообщениями об ошибках и inflection
  для embed (`person` и `people`) проверены против Node в `json-server-js` каждый по отдельности.
- `db.data[name]` читает `Object.prototype`: `/__proto__` отвечает `{}`, `/constructor` пустым
  200, а `PATCH /__proto__` заменяет прототип базы данных, что видят последующие обращения.
- HTTP-парсер Node отвечает 400 и закрывает соединение на необработанных не-ASCII путях и неизвестных методах.

Найдено в json-server: после каждой собственной записи его наблюдатель за файлами перечитывает файл. Когда
следующий запрос пишет раньше, чем это перечитывание завершится, оно может стереть эту запись: в первой
записи, отправленной так быстро, как отвечал сервер, был POST с ответом 201, который последующие чтения не
показывали. `app record --pace 50` выжидает между запросами, и кейсы записаны именно так. Порт
перечитывает файл, только когда его изменил кто-то другой, поэтому не теряет эту запись: это намеренное
различие.

Бенчмарк: Apple M4 (10 ядер, 16 GB), macOS 27.3, Node 24.15.0 запускает `lib/bin.js` в том виде, в каком его
собирает `tsc` для npm, Rust-бинарник собран с `--release`. Оба отдают копию одной и той же
базы данных по loopback; `ab -k` отправляет одинаковые запросы, по 20,000 на строку (40 для медленного embed на
большой базе) после прогрева. Два прогона, каждый запущен при средней нагрузке за 1 минуту ниже 3;
в ячейках прогон 1 / прогон 2 в запросах в секунду. Скрипт: [`bench/bench.py`](https://github.com/marprojector/everything-rust/blob/main/demo/real-world/json-server-rs/bench/bench.py).

Где разрыв мал: одно соединение читает весь список из 10,000 постов (1.2x: оба тратят
время на печать 1.5 MB JSON), записи в большую базу (от 1.1 до 1.2x: оба переписывают весь
файл 3.6 MB при каждой записи, а Rust объединяет записи из очереди, как это делает lowdb) и поиск по заголовкам с сортировкой
на одном соединении (1.4x). Большой выигрыш даёт конкурентность, которой у процесса Node
нет, и embed, где json-server фильтрует каждый комментарий для каждого поста (порт
индексирует комментарии один раз на запрос, результат тот же).

Первый поднятый бинарник был медленнее Node на большой базе (33 против 298 запросов в
секунду для всего списка, 39 против 217 для записей). Профилирование нашло, по порядку: отсутствие
`TCP_NODELAY` (каждый большой ответ ждал около 40 ms отложенного ACK), клонирование всей базы данных
для добавления `$schema` перед каждой записью, клонирование каждого элемента списка перед печатью, одна блокировка
на все запросы и хеширование `item.id` через SipHash для каждого из 10,000 элементов. Всё исправлено; 3,399
кейсов модулей и 514 HTTP-кейсов проходят после каждого изменения.

Найдено в инструменте и исправлено:

- Сервер, который записывает своё состояние, нельзя было записать дважды из одного и того же начального состояния:
  теперь `--fresh <path>` копирует базу данных (и `public/`) в свежий рабочий каталог при каждом
  запуске, из снимка, хранящегося вместе с кейсами; `--arg` передаёт каждой сборке аргументы оригинала;
  `--pace` описан выше.
- `bridge` оставлял `paginate<T>(items: T[])` на TS (дженерик по чему угодно, включая функции);
  `--as-json T` подключает его через мост как JSON-значения.
- Маршруты входной точки с параметрами отвечали собственным 400 от axum на `/posts/%E0` ещё до того, как
  модуль видел запрос; теперь параметры читаются из URI.
- `lift` подготавливал только подключённый модуль, но не крейты, от которых тот зависит по пути, и писал `lib.rs`,
  который отвергал `cargo fmt --check`; исправлено и то, и другое.
- Генерируемые им серверы не устанавливали `TCP_NODELAY`: ответ, записанный в две части, ждал
  отложенного ACK от клиента, около 40 ms. Теперь они его устанавливают.

Что не покрыто: базы данных в JSON5 (бинарник сообщает об этом и завершается), ограничение тела в 100 KiB
(в Node оно зависит от того, как тело приходит порциями по 64 KiB; порт предполагает полные чтения), строки
с одиночными суррогатами (они становятся U+FFFD) и значение `1e400` в базе данных (Node держит `Infinity`
в памяти до следующего перечитывания; порт сохраняет `null`, который и попадает в файл).

# Реальный код на шести языках

everything-rust был прогнан от начала до конца (analyze, bridge, record, port, diff, gate, bench) на реальном коде на
каждом поддерживаемом языке. Код должен был уже находиться на этой машине: код, скачанный из
интернета, не выполнялся. Поэтому целями стали модули стандартных библиотек, поставляемые с
установленными тулчейнами, а для Java и C, где на диске не нашлось подходящих исходников библиотек, эталоном за тонким фасадом
служат сами JDK и glibc.

Порты, записанные кейсы и дополнительные входные данные лежат в [`demo/real-world`](https://github.com/marprojector/everything-rust/blob/main/demo/real-world/README.md).

| Язык | Код | Функции | Записанные кейсы | Результат |
| --- | --- | ---: | ---: | --- |
| Go | `path` из стандартной библиотеки Go 1.24 | 7 (+1 оставлена) | 2,642 (542 из собственных тестовых таблиц Go) | 2,642/2,642, gate проходит |
| Ruby | `shellwords.rb` из Ruby 3.3 | 3 | 1,617 (446 с raise) | 1,617/1,617, gate проходит |
| Python | `colorsys.py` из CPython 3.13 | 6 | 2,400 | 2,400/2,400, gate проходит |
| Java | JDK 21 за фасадом (`Integer`, `Long`, `Math`, `Double.toString`, `URLEncoder`, `Base64`, `toUpperCase`) | 11 | 4,492 (226 с исключением) | 4,492/4,492, gate проходит |
| C | glibc за фасадом (`strtol`, `atoi`, `strtod`, `strspn`, `strcmp`, ctype) | 9 | 1,860 (6 с падением) | 1,859/1,859 после удаления одного кейса с неопределённым поведением, gate проходит |
| C | aklomp/base64 (вендорен в runtime mypyc) | 0 из 7 | - | только план: каждая функция принимает выходные буферы или структуру состояния |

## Скорость

Первые мосты для Python, Go, Ruby и Java передавали каждый аргумент и результат через текст JSON,
что стоило в 10-50x больше, чем работа в этих функциях. Их переделали так, чтобы они преобразовывали
значения напрямую. Теперь `bench` замеряет только вызовы (аргументы декодируются один раз, внутри процесса) и говорит,
выкатывать ли порт.

| Язык | На вызов раньше | На вызов сейчас | Rust против оригинала (`bench`, среднее геометрическое) | Вердикт |
| --- | ---: | ---: | --- | --- |
| Ruby | 6.9-9.5 µs (Fiddle + JSON) | 0.36-1.15 µs (расширение magnus) | **в 4.4x быстрее** (3.6-7x на функцию) | выкатывать |
| Python | 11.7 µs (JSON) | около 0.3 µs (прямое преобразование PyO3) | **в 1.35x быстрее** (1.5-1.9x на большинстве вызовов) | выкатывать |
| C | - | без пересечения: прямая компоновка | 0.87x: ctype быстрее в 1.1-1.4x, оптимизированные в glibc `strtod`, `strspn`, `strcmp` 0.5-0.7x | оптимизировать или оставить более медленные |
| Java | около 1.7 µs (JNI + JSON) | 30-800 ns (типизированный JNI и бинарный протокол) | 0.18x | портировать модули покрупнее |
| Go | 2.6 µs (cgo + JSON) | 0.11-0.42 µs (типизированный cgo и бинарный протокол) | 0.04x | портировать модули покрупнее |

Списки, map, структуры и несколько результатов в Go и Java передаются через бинарный протокол, генерируемый для каждого
типа: `WordFreq` в Go (map) ускорился с 5.1 до 1.0 µs, `Midpoint` (структура) с 7.2 до 1.0 µs;
`frequencies` в Java (`Map`) с 8.4 до 1.0 µs, а `words` (`List<String>`) с 6.0 µs до
0.57 µs, что в 1.39x быстрее самой Java.

TypeScript (ядро x18n, девять модулей, 27 функций на тех же кейсах): бинарный протокол снизил
стоимость моста в среднем на треть (`rangeContains` 3.6 -> 1.1 µs, `applyTextEdits` 10.4 -> 5.7
µs, `toWireRange` 5.0 -> 2.6 µs), а `buildTree` перешёл от паритета к ускорению в 2.0x относительно TS.
Остальные функции листовые, V8 выполняет их за 15-600 ns: на Rust они по-прежнему медленнее, как и для Go и Java.

От чего это зависит:

- **Интерпретируемые оригиналы (Python, Ruby)**: вызов в Rust стоит около 100-300 ns, а
  код на Rust гораздо быстрее интерпретатора, так что выигрывают даже маленькие функции.
- **Компилируемые оригиналы (Go, Java после JIT)**: исходная листовая функция занимает 4-90 ns; один
  вызов cgo сам по себе стоит около 80 ns, вызов JNI со строками ещё дороже. Никакой мост не сделает функцию на 5 ns
  быстрее. Эти языки выигрывают, только когда один вызов делает много работы: портируйте функцию
  вместе с вызывающим её кодом. `bench` так и говорит.
- **C**: пересечения границы нет; код на Rust сравнивается с кодом на C напрямую, и результат
  определяется самим портом.

### Пакеты: поиск в x18n

Порты листовых функций выше измерены на вызов. На поиске в боковой панели x18n (50,000 ключей, ввод по
букве) `everything-rust profile` показал, что `fuzzyScore` занимает около четверти прогона и вызывается по разу на каждый ключ из
`matched`, и предложил `--batch fuzzyScore:text`. Сгенерированный `FuzzyScoreBatch` хранит
ключи в Rust; `FuzzyScoreIndex` в `port.rs` один раз переводит их в нижний регистр в UTF-16 и хранит 64-битную
маску кодовых единиц каждого ключа, так что большинство ключей, которые не могут совпасть, пропускаются без чтения. Результаты
идентичны конвейеру TS для каждого запроса:

| | ms на запрос | против TS |
| --- | ---: | ---: |
| Конвейер TS | 10 | 1x |
| TS с тем же сужением | 4.1-5.4 | 2x |
| Пакет, индекс по умолчанию (порт на элемент, 4 ядра) | 5.1 | 1.7x |
| Пакет с `FuzzyScoreIndex` (маски), napi, 4 ядра | 1.2 | 7x |
| Пакет с `FuzzyScoreIndex`, ранжирующим сам, napi, 4 ядра | 0.45-0.56 | 18-22x |
| То же, wasm, 1 поток | 0.95 | 11.5x |

Шаг от 7x к 20x: из 1.2 ms 0.4 ms приходились на собственный `Array.from(order, i =>
keys[i])` бенчмарка (обычный цикл стоит 0.02 ms). Остальное дало то, что индекс стал ранжировать сам:
он пересчитывает только совпадения последнего запроса, когда новый запрос его продолжает (ключ, который не
совпадает с `s`, не может совпасть с `se`), читает однобуквенные запросы из таблицы первых позиций, оценивает
ASCII-ключи как байты и упорядочивает целочисленные оценки сортировкой подсчётом. Callgrind показал, что
библиотечные вызовы (`memchr`, `memcmp`) обходятся дороже обычных циклов на ключах длиной 30 байт. Часть выигрыша
даёт алгоритм, поэтому бенчмарк также запускает TS с тем же сужением: Rust быстрее в 7-12x
даже его (wasm в 5x).

Тот же приём в других языках, против оригиналов (4 ядра, идентичные результаты и
ошибки):

| Язык | Нагрузка | Оригинал | Порт с вызовом на элемент против оригинала | Пакет против оригинала |
| --- | --- | ---: | ---: | ---: |
| Python | `slugify` из фикстуры, 20,000 строк | 98 ms | - | 17x |
| Ruby | `slugify` из фикстуры, 20,000 строк | 110 ms | - | 12.7x |
| Ruby | `Shellwords.shellescape`, 50,000 смешанных значений | 88 ms | - | 11.8x |
| Go | `Slugify` из фикстуры, 50,000 строк | 49 ms | 0.93x | 3.3-4.1x |
| Java | `slugify` из фикстуры, 50,000 строк | 43 ms | 0.68x | 3.0x |

Пакет для Go поначалу работал медленнее одного потока: порт выделяет память на каждый элемент, и аллокатор glibc
сериализовал потоки внутри процесса Go. Пакетные крейты теперь используют mimalloc. Пакет shellescape
также нашёл баг в порте, который пропустила запись с вызовом на каждый элемент: символы Ruby (`shellescape(:sym)`) возвращались
в виде своего JSON-маркера. Исправлено в порте.

Затем Go и Java выросли с 2.5x и 1.7x до 4x и 3x. Внутри пакета половина времени уходила не на
работу: результаты склеивались и освобождались в одном потоке, Go копировал их второй раз, а Java
делала по одному вызову JNI на строку через modified UTF-8. Теперь строковые результаты возвращаются целиком, записываясь
на всех ядрах в собственный буфер Go или в один `char[]` Java. Другая половина приходилась на сами порты: в одном
потоке `slugify` на Rust был едва быстрее версии на Go и медленнее JIT в Java. Перевод ASCII в нижний регистр
без обращений к таблицам и без промежуточной строки это исправил; порт для Java сохраняет
правило конечной сигмы, переводя в нижний регистр целиком только тот отделённый пробелами фрагмент, который содержит `Σ`.
На вызов порт для Go вырос с 0.73x до 0.93x, порт для Java с 0.46x до 0.68x.

## Что нашли прогоны

### Баги в everything-rust, исправлены

- **Float менялись на один ULP** (прогон Java). Парсер float по умолчанию в `serde_json` не всегда
  округляет корректно. everything-rust искажал записанные входные данные при их чтении, а сгенерированные крейты
  искажали их снова. 43 кейса `Double.toString` падали для корректного порта. Исправлено с помощью
  фичи `float_roundtrip` из `serde_json` в everything-rust и в каждом генерируемом им крейте (napi-rs,
  wasm и JSON-диспетчер).
- **Падения C обрывали запись** (прогон C). Входные данные вне контракта функции C (`isalpha(INT_MAX)`)
  вызывают segfault в glibc. Теперь драйвер C запускает каждый кейс в дочернем процессе через fork и записывает
  `crash: SIGSEGV`; `diff` принимает здесь любое поведение порта, поскольку поведение C не определено.
- **`module_function :name` не распознавался** (прогон Ruby). `shellwords` объявляет свои функции модуля
  с аргументами-символами после методов; экспортёр знал только голую форму `module_function`.
  Теперь находятся обе формы.
- **Нетипизированный код получал мусорные входные данные** (прогон Python). В `colorsys` нет аннотаций типов, поэтому 1,709 из
  1,800 сгенерированных кейсов были `TypeError`. Параметры без аннотаций, используемые как числа (`r - g`,
  `max(r, g, b)`, `x < 1`), теперь получают тип `number`, в Python и Ruby: осталось 94 ошибки, все настоящие
  (`ZeroDivisionError`).
- **Int, передаваемые вместо float, никогда не записывались** (прогон Python). Вызывающий код на Python передаёт `1` так же часто, как
  `1.0`, а `colorsys` пропускает int как есть (`hsv_to_rgb(0, 0, 7)` даёт `(7, 7, 7)`). Теперь при записи
  целочисленные значения передаются как int в каждом четвёртом кейсе Python; это выявило 134 расхождения в
  порте с типом `f64`.
- **Сообщения со времён TypeScript**: «must stay in JS», «kept in TS», «characterization tests
  against the TS code» теперь называют исходный язык.
- **Повторно открытые базовые классы** (`class String` в `shellwords.rb`) теперь считаются риском monkeypatching.

### Поведение, которому должен соответствовать порт, найденное `diff`

Каждая строка была расхождением в первом порте, пойманным записанными кейсами. Строки с пометкой *фикстура*
взяты из небольших тестовых проектов в `tests/fixtures/`, написанных для каждого языка; остальные из
прогонов на реальном коде выше.

- Go `path.Clean`: `lazybuf` в Go читает байт по индексу записи после того, как тот сдвинулся назад, а не
  последний сохранённый байт (9 кейсов, из собственной тестовой таблицы Go).
- *фикстура* `strings.ToLower` в Go и `downcase` в Ruby переводят в нижний регистр каждую руну отдельно: `ΣΊΣΥΦΟΣ` становится `σίσυφοσ`,
  тогда как `to_lowercase` в Rust применяет правило конечной сигмы. Go также отображает `İ` в `i`, а Rust
  даёт `i̇`.
- *фикстура* Go режет строки по байтам; разрез посреди руны доходит до JSON как по одному U+FFFD на каждый байт.
- *фикстура* `slugify` в Ruby выбрасывал `NoMethodError` для отрицательного `max` (`slug[0, -1]`
  даёт `nil`): баг в оригинале, который порт должен сохранить, либо сначала нужно исправить вызывающий код.
- *фикстура* `Array#sum` в Ruby использует суммирование Кэхэна-Бабушки и начинает с целого 0, поэтому `[-0.0].sum` равно `0.0`.
- `Float#to_s` в Ruby использует экспоненциальную запись начиная с 1e15 (`1e15.to_s` даёт `1.0e+15`, `1e14.to_s` даёт
  `100000000000000.0`); `nil.inspect` внутри массивов даёт `nil`.
- *фикстура* `\s` в Java распознаёт только ASCII; `split_whitespace` в Rust также разбивает по U+00A0.
- Результаты Python «int или float»: `colorsys` сохраняет int при `+`, `-` и `*`, поэтому точный порт
  вычисляет с небольшим типом «int или float» вместо `f64` (134 кейса после того, как начали записываться int).
- `strtod("-")` в glibc ничего не преобразует и возвращает `+0.0`, а не `-0.0`.

Учтено в первом порте и подтверждено записанными кейсами:

- `Integer.parseInt` в Java принимает любую десятичную цифру Unicode (`١٢`, `２`) через `Character.digit`.
- `Double.toString` в Java (JDK 19+) печатает кратчайшую десятичную запись, но не меньше двух цифр:
  `4.9E-324`, тогда как кратчайшая форма в Rust `5e-324`.
- `max(nan, 1, 2)` в Python равно `nan` (побеждает первое значение, если только более позднее не окажется больше при сравнении);
  `-0.0 % 1.0` равно `0.0`.
- `toupper(-128)` в glibc равно `128` (его таблицы принимают знаковые значения `char`); `strtol` с основанием 0
  читает `077` как восьмеричное, а `0x` без шестнадцатеричной цифры как `0`.

### Ограничения, которые показали эти прогоны

- **API C, передающие буферы.** Публичные функции aklomp/base64 принимают `char *out, size_t *outlen`
  или `struct base64_state *`. Мост C передаёт только скаляры и `const char *`, поэтому оставляет
  их все на C, с указанием причины. Поддержка шаблона с выходным буфером станет следующим шагом для C.
- **Макросы C.** 43 из 51 файла base64 определяют функции через макросы
  (`BASE64_ENC_FUNCTION(arch)`); парсер сообщает там об ошибках, и план помечает такие модули как
  частичные. Интринсики SIMD пока не отмечаются как риск.
- **Неопределённое поведение, которое не приводит к падению.** `ispunct(1000)` читает за пределами таблицы glibc и
  возвращает 1. Ни один порт не должен это копировать; этот единственный кейс был удалён из `cases.jsonl` вручную.
  Встроенного способа пометить кейс как неопределённый пока нет.
- **Динамическая типизация стоит кода.** Порт `shellwords` заново реализует `to_s` и `inspect` из Ruby
  для чисел, nil, массивов и хешей, потому что `shellescape` принимает что угодно. Порту `colorsys`
  нужна числовая башня Python. Типизированный порт короче, но меняет поведение для части
  вызывающего кода; `diff` показывает, для какого именно.
- **Фасады.** Прогоны Java и C проверяют настоящее поведение JDK и glibc, но через фасады,
  написанные для прогона, а не через собственный API библиотеки.

## Как работает каждый язык

| | Запись | Diff | Мост | Теневой режим |
| --- | --- | --- | --- | --- |
| Go | сгенерированный драйвер, собранный как отдельный модуль с `replace` на оригинал | тот же драйвер поверх обёртки cgo | JSON-диспетчер + пакет cgo с исходным API | пакет с исходным API, запускает обе версии |
| Ruby | сгенерированный драйвер загружает исходные файлы | тот же драйвер загружает обёртку Fiddle | JSON-диспетчер + обёртка Fiddle, определяющая те же модули | файл, подключаемый через require после оригинала: делает `prepend` обеих версий |
| Java | драйвер на рефлексии, скомпилированный с исходниками оригинала | тот же драйвер, скомпилированный с классами-обёртками JNI | JSON-диспетчер поверх JNI + классы-обёртки с исходными статическими методами | классы `<Class>Shadow` |
| Python | драйвер внутри процесса импортирует оригинал | тот же драйвер импортирует пакет PyO3 | PyO3 | модуль с исходным API |
| C | `cc -shared` оригинала, вызов через ctypes, отдельный fork на кейс | ctypes поверх Rust `cdylib` | функции `extern "C"` с исходными именами и заголовочный файл | теневой `.c` с переименованиями через `-D`; фича `shadow` крейта экспортирует только имена `everything_rust_` |

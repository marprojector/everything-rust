# Профилирование и анализ

## Profile: найти то, что стоит переносить

Когда цель в скорости, измеряйте, прежде чем что-либо выбирать:

```sh
everything-rust profile <repo> -- node bench.mjs      # или: python3 bench.py, ruby bench.rb,
                                                    #      java -cp out Main, go test -run X -bench . ./pkg
```

`profile` запускает реальную нагрузку под профилировщиком языка (node, cProfile, pprof через `go test`, JFR, трассировщик Ruby) и перечисляет горячие функции по инклюзивному времени, их вызывающий код и то, какие циклы стоит пакетировать. Go профилируется только через `go test`; C не поддерживается.

- Маленькую функцию, вызываемую по разу на каждый элемент, **не** стоит портировать отдельно: один вызов в Rust стоит больше её работы, а JIT (V8, JVM, Go) выполняют её за наносекунды. Портируйте её вместе с вызывающим кодом или [пакетируйте](/docs/concepts/batches). Строка совета говорит, что именно, с точной командой.
- Уже скомпилированный код (numba `@njit`, Cython, `@jax.jit`) выполняется как машинный код: порт на Rust почти не даёт выигрыша в скорости. `profile` перечисляет его в разделе «Already compiled».

## Analyze: спланировать порт

```sh
everything-rust analyze <repo> -o plan.md        # для людей
everything-rust analyze <repo> --json            # для агентов: схема everything-rust/analyze@1
everything-rust analyze <repo> --whole-app       # плюс точки входа, форма, зависимости, решения
```

`analyze` перечисляет модули, порядок портирования, риски с `file:line`, мост для каждого модуля, насколько хорошо каждая зависимость отображается на крейт, и `start_here`: лучшие первые порты. `--whole-app` добавляет форму приложения (CLI, сервер или библиотека) и точки входа, каждую зависимость (импортированную или объявленную) с её крейтом, части (модули, импортирующие друг друга, переносятся вместе) и пронумерованные решения с рекомендуемым ответом. См. [Портирование целого приложения](/docs/whole-apps/overview).

- Пакеты (`package.json`) и исходные файлы; пропускает `node_modules`, результаты сборки, фикстуры,
  песочницы, конфиги инструментов. Блоки `<script>` в Vue/Svelte/Astro разбираются на импорты.
- **Модули**: каталог исходных файлов или файл в корне исходников пакета.
- **Волны**: импорты модуля попадают в более ранние волны; циклы импортов портируются вместе.
- **Мост**: napi-rs, когда модулю или чему-то, что он импортирует, нужен Node; wasm-bindgen для переносимого
  кода; оставить на JS для кода UI и редактора.
- **Готовность** (насколько безопасно) и **приоритет** (безопасно и стоит того: циклы и работа со строками, тесты, размер).

| Риск | Серьёзность | Пример |
| --- | --- | --- |
| Смещения в строках | высокая | `slice`, `indexOf`, `matchAll`, флаг `d`: UTF-16 против UTF-8 |
| Синтаксис регулярных выражений | высокая | lookaround, обратные ссылки, `y`: нет в крейте `regex` |
| Динамические регулярные выражения | высокая | `new RegExp(userPattern)`: синтаксис JS во время выполнения |
| Динамический код | высокая | `eval`, `new Function`, вычисляемый `import()` |
| Динамическая типизация | средняя | `any`, `'key' in value` |
| Упорядоченные коллекции | средняя | `Map`, `Set`, `Object.keys`: порядок вставки |
| Async, генераторы | средняя | границы промисов и генераторов |
| Наследование классов, рефлексия | средняя | `extends`, `Proxy`, `Reflect`, `Symbol` |
| API на колбэках | средняя | параметры и методы функционального типа: «болтливые» мосты |
| Исключения, числа, JSON | низкая | `throw`, побитовые операции, порядок в `JSON.stringify` |
## Крейты для зависимостей {#crates-for-dependencies}

`analyze` называет Rust-крейт для каждой библиотеки, которую импортирует код, со степенью соответствия `good`, `partial` или `none`. Библиотека, отсутствующая в его таблице, отмечается как `unknown`; таблица никогда не угадывает крейт. Чтобы добавить его, см. [Участие в проекте](/docs/project/contributing#add-a-crate-mapping).

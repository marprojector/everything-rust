# Цикл работы

Каждый порт, от одной горячей функции до целого приложения, проходит одни и те же шаги, по одному модулю за раз. Порт готов, только когда проходит `gate`.

Как everything-rust проверяет порт, что решают его команды и где проходят его границы. Назад к [README](/).

## Как это работает {#how-it-works}

```
profile ──> analyze ──> bridge ──> record ──> port.rs ──> diff ──> bench ──> shadow ──> gate
 where the    what to     the Rust   what the    you or      every     faster?    both side   done means
 time goes    port first  crate and  original    your agent  recorded  the        by side in  this passes
                          wrapper    does        write it    case      verdict    production
```

Оригинал остаётся источником истины: `record` запускает его на граничных случаях (и ваших собственных входных данных) и
сохраняет то, что он возвращает или выбрасывает; `diff` воспроизводит каждый кейс на Rust; ничего не выходит в релиз, пока
все они не совпадут и не пройдёт `gate`. Вызывающий код всё это время сохраняет исходный API.

Целое приложение проходит тот же цикл модуль за модулем, внутри рамки, которая доказывает корректность всей
программы ([Портирование целого приложения](/docs/whole-apps/overview)):

```
analyze --whole-app ──> app record ──> app front-door ──> per unit: the loop above, then app wire ──> app lift
 shape, every           what the app    Rust owns the       gate passes, so the unit answers in         pure Rust,
 dependency, the        does from the   entry point; the     Rust: replay 100%, fallback rate down      proved by
 decisions to make      outside         original answers                                                replay
```

## Цикл работы {#the-loop}

| Шаг | Команда | Что делает |
| --- | --- | --- |
| 0. Профилирование | `everything-rust profile <repo> -- node bench.mjs` | Запускает реальную нагрузку под профилировщиком языка (node, cProfile, pprof через `go test`, JFR, трассировщик Ruby): горячие функции по инклюзивному времени, их вызывающий код и то, какие циклы пакетировать; отмечает уже скомпилированный код (numba, Cython, JAX), где Rust почти ничего не даёт |
| 1. План | `everything-rust analyze <repo>` | Модули, порядок портирования, риски с `file:line`, мост для каждого модуля, соответствие зависимостей крейтам, лучшие первые порты; `--whole-app` добавляет точки входа и форму, каждую зависимость (импортированную или объявленную) с её крейтом, части (модули, импортирующие друг друга, переносятся вместе) и пронумерованные решения с рекомендуемым ответом |
| 2. Мост | `everything-rust bridge <repo> <unit>` | Крейт с привязками (`lib.rs` плюс обёртка, которую загружает исходный язык) и заглушками для портирования (`port.rs`); `--batch fn:param` добавляет класс, который хранит много значений `param` в Rust; `--as-json T` подключает через мост как JSON-значения параметр типа, который приложение наполняет только данными |
| 3. Запись | `everything-rust record <crate>` | Запускает оригинал на сгенерированных граничных случаях (не-ASCII, эмодзи, `-0`, `NaN`, целые там, где ожидаются float, ...) и на каждой семантической ловушке в каждом параметре (длина и регистр строк, деление со знаком, границы переполнения, печать float, порядок в map и порядок сортировки) и сохраняет `cases.jsonl`; `--from-tests -- npx jest` (или `-- pytest`) также записывает каждый вызов, который делает собственный набор тестов оригинала; `--float-tolerance 1e-9` позволяет float в численном коде совпадать в пределах этой доли |
| 3. Сборка | `everything-rust build <crate>` | Собирает сторону Rust: `.node`, пакет wasm, расширение Python или разделяемую библиотеку |
| 3. Diff | `everything-rust diff <crate>` | Воспроизводит записанные кейсы на Rust, вызывая его так, как его вызывает код, использующий оригинал; перечисляет расхождения |
| 3. Бенчмарк | `everything-rust bench <crate>` | Замеряет время записанных кейсов на оригинале и на Rust, включая мост |
| 4. Теневой режим | `everything-rust shadow <crate>` | Замена, которая запускает обе версии, возвращает результат оригинала и сообщает о расхождениях; `EVERYTHING_RUST_MODE=old\|shadow\|new` |
| 5. Гейт | `everything-rust gate <crate>` | fmt, clippy `-D warnings`, тесты, аудит `unsafe`, ничего непортированного, записанный кейс с ошибкой для каждого пути ошибки оригинала, никаких `unwrap`/`expect`/`panic!` там, где оригинал возвращает ошибку (если только не помечено `// INFALLIBLE: <why>`), сборка, API, поведение |
| Агенты | `everything-rust setup` | Регистрирует MCP-сервер (`everything-rust mcp`, каждый шаг как инструмент) и навык рабочего процесса ([`skills/everything-rust/SKILL.md`](https://github.com/marprojector/everything-rust/blob/main/skills/everything-rust/SKILL.md)) в ваших агентах разработки |

## Горячие пути: держите данные в Rust {#hot-paths-keep-the-data-in-rust}

Порт, вызываемый по разу на каждый элемент, платит за мост за каждый элемент и проигрывает JIT. Выигрывает
перенос цикла: `profile` находит его, а `--batch` генерирует класс, который принимает элементы один раз
и выполняет функцию над всеми ними за вызов, на всех ядрах, с результатами в типизированных массивах.

```sh
everything-rust profile ../x18n -- node --experimental-strip-types $PWD/demo/x18n-search/search.ts .
# -> fuzzyScore: четверть всего прогона, вызывается на каждый ключ из `matched`: нужно пакетировать
everything-rust bridge ../x18n packages/core/src/fuzzy.ts --batch fuzzyScore:text
```

```js
const search = new FuzzyScoreBatch(keys)          // once
const order = search.rank(query, 0)               // per keystroke: indexes, best first
```

Структура `FuzzyScoreIndex` в `port.rs` заменяет цикл по умолчанию циклом, который подготавливает
элементы один раз и умеет ранжировать сам (`rank`): она хранит ключи в нижнем регистре с маской символов
для каждого, таблицу первой позиции каждого частого символа в каждом ключе (запрос из одной буквы занимает один
столбец) и совпадения последнего запроса (ввод `se` после `s` пересчитывает только то, что совпало с `s`). На
поиске в боковой панели x18n по 50,000 ключей, при вводе по букве, с идентичными результатами:

| | На запрос | против TS |
| --- | ---: | ---: |
| TS: `map(fuzzyScore)`, filter, sort | 10 ms | 1x |
| TS с тем же сужением, что и в индексе | 4.1-5.4 ms | 2x |
| Тот же порт, вызываемый на каждый ключ | - | 0.2-0.4x |
| `FuzzyScoreBatch`, индекс по умолчанию (4 ядра) | 5.1 ms | 1.7x |
| `FuzzyScoreBatch` с `FuzzyScoreIndex` (napi, 4 ядра) | 0.45-0.56 ms | **18-22x** |
| То же с wasm (один поток) | 0.95 ms | **11.5x** |

По сравнению с TS, выполняющим то же сужение, Rust всё равно быстрее в 7-12x (wasm в 5x). Превращайте возвращённые
индексы в ключи обычным циклом: `Array.from(order, i => keys[i])` обходился в 20x дороже, 0.4 ms.

Пакеты есть у каждого языка, и они обгоняют оригинал даже там, где порты с вызовом на каждый элемент проигрывают.
Та же работа на 4 ядрах, идентичные результаты и ошибки (бенчмарки в каждом каталоге demo):

| Язык | Нагрузка | Оригинал | Порт с вызовом на элемент против оригинала | Пакет против оригинала |
| --- | --- | ---: | ---: | ---: |
| TS | поиск x18n, 50,000 ключей | 10 ms | 0.2-0.4x | **20x** |
| Python | `slugify`, 20,000 строк | 98 ms | - | **17x** |
| Ruby | `slugify`, 20,000 строк | 110 ms | - | **12.7x** |
| Ruby | `shellescape` (stdlib), 50,000 смешанных значений | 88 ms | - | **11.8x** |
| Go | `Slugify`, 50,000 строк | 49 ms | 0.93x | **4x** |
| Java | `slugify`, 50,000 строк | 43 ms | 0.68x | **3x** |

Компилируемые оригиналы выигрывают меньше: работа на элемент и так быстрая, поэтому пакет выигрывает за счёт числа
ядер. Пакетные крейты выделяют память через mimalloc: с системным аллокатором пакет для Go был медленнее
одного потока. Демо: [`demo/x18n-search`](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-search/README.md).

## Что решает `bridge` {#what-bridge-decides}

- Экспорты, которые не могут пересечь мост, остаются на исходном языке с указанием причины, а теневой
  модуль реэкспортирует оригинал. Для TS:
  функции, которые принимают или возвращают функции, генераторы и итераторы, RegExp, проверки `instanceof`,
  дженерики (`--as-json T` подключает через мост тот, который приложение наполняет только данными) и значения, типы которых (с учётом импортов, реэкспортов и `extends`) содержат
  функции. `--keep "name: reason"` оставляет больше, например код, зависящий от данных `Intl`.
- Типы TS отображаются в типы Rust, псевдонимы типов разрешаются через импорты, а типы параметров
  выводятся из значений по умолчанию; структурированные значения передаются через сгенерированный бинарный протокол (JSON только
  как запасной вариант для форм, которые протокол не моделирует).
- JSON не может выразить `undefined`, NaN, Infinity, -0 или одиночные суррогаты: структурированные значения несут
  маркеры (`{"$undefined": true}`, `{"$num": "NaN"}`, `{"$utf16": [...]}`), которые транслирует сгенерированный
  `index.cjs`, с хелперами в `js.rs` крейта.

`record` выполняет исходники TS как есть: хук разрешения модулей Node следует импортам в стиле бандлеров
(`./errors` в `./errors.ts`), `--resolve-from` подставляет npm-пакеты, когда в репозитории они не
установлены, а TS, требующий трансформации (enum, parameter properties), запускается повторно с
`--experimental-transform-types`.

## Что анализирует `analyze` {#what-analyze-looks-at}

- Пакеты (`package.json`) и исходные файлы; пропускает `node_modules`, результаты сборки, фикстуры,
  песочницы, конфиги инструментов. Блоки `<script>` в Vue/Svelte/Astro разбираются на импорты.
- **Модули**: каталог исходных файлов или файл в корне исходников пакета.
- **Волны**: импорты модуля попадают в более ранние волны; циклы импортов портируются вместе.
- **Мост**: napi-rs, когда модулю или чему-то, что он импортирует, нужен Node; wasm-bindgen для переносимого
  кода; оставить на JS для кода UI и редактора.
- **Готовность** (насколько безопасно) и **приоритет** (безопасно и стоит того: циклы и работа со строками, тесты, размер).

| Риск | Серьёзность | Пример |
| --- | --- | --- |
| Смещения в строках | высокая | `slice`, `indexOf`, `matchAll`, флаг `d`: UTF-16 против UTF-8 |
| Синтаксис регулярных выражений | высокая | lookaround, обратные ссылки, `y`: нет в крейте `regex` |
| Динамические регулярные выражения | высокая | `new RegExp(userPattern)`: синтаксис JS во время выполнения |
| Динамический код | высокая | `eval`, `new Function`, вычисляемый `import()` |
| Динамическая типизация | средняя | `any`, `'key' in value` |
| Упорядоченные коллекции | средняя | `Map`, `Set`, `Object.keys`: порядок вставки |
| Async, генераторы | средняя | границы промисов и генераторов |
| Наследование классов, рефлексия | средняя | `extends`, `Proxy`, `Reflect`, `Symbol` |
| API на колбэках | средняя | параметры и методы функционального типа: «болтливые» мосты |
| Исключения, числа, JSON | низкая | `throw`, побитовые операции, порядок в `JSON.stringify` |

## Чего он не поймает {#what-it-cant-catch}

Прохождение означает, что Rust совпадает с каждым записанным кейсом, и не более того. То, что больно бьёт по переписываниям,
обычно находится за пределами записи, поэтому знайте, где проходят границы:

- **Входные данные, которые никто не записал.** Сгенерированные кейсы, ловушки, набор тестов оригинала
  (`record --from-tests`) и ваши собственные `--inputs` задают потолок. Добавляйте реальные входные данные (выборки из
  продакшена, баг-репорты); пользовательский ввод, который ломает прод, редко бывает тем, что придумает генератор.
- **Оригинал, который ушёл вперёд.** `record` сохраняет отпечаток файлов модуля
  (`recorded-from.json`); когда оригинал позже меняется, `diff` предупреждает, а `gate` падает, пока вы
  не запишете заново, вместо того чтобы проходить против того, что оригинал делал раньше.
- **Регулярные выражения.** В крейте `regex` нет lookaround и обратных ссылок, и даже шаблон, который
  компилируется, может обрабатывать `\w`, `\b`, `\d` и регистронезависимое сопоставление на тексте не-ASCII иначе,
  чем JS, Python или Java. Замена на `fancy-regex` или переписывание шаблона может пройти каждый
  записанный кейс и всё равно отличаться на турецкой `ı` без точки или на zero-width joiner. `record` добавляет
  ловушки для регулярных выражений (перечисленные, знак Кельвина, длинная s, арабско-индийские цифры, разделители строк, конечная сигма)
  к каждой функции в файле, который использует регулярные выражения, но прогоняйте фаззингом и свои реальные шаблоны на реальном тексте.
- **То, что меняется между прогонами.** `record` запускает оригинал дважды и разбирает, что различалось:
  изменившиеся значения (время, идентификаторы) становятся шаблонами; те же строки в другом порядке (хеш-таблицы,
  конкурентность) сравниваются в любом порядке, так что порт всё равно должен выдать именно эти строки;
  другое количество строк становится `...`, что совпадает с чем угодно. `record` перечисляет каждый вид:
  просмотрите каждый, поскольку разница в порядке хеша или в конкурентности именно то, что в порте может
  измениться по-настоящему.
- **Float.** Преобразование чисел в текст различается между языками (`1e21`, `-0`, количество цифр).
  Ловушки включают эти значения, и они должны совпадать точно; `--float-tolerance` прощает
  только округление, но никогда не форматирование.
- **Всё, чего нет в выводе.** Время выполнения, память, конкурентность под нагрузкой и побочные эффекты помимо
  stdout, stderr, кодов возврата, записанных файлов и HTTP-ответов (сетевые вызовы, базы данных,
  сигналы) не сравниваются.
- **Другие платформы.** Запись доказывает поведение на той машине, где она была сделана. Код на C, результаты которого
  зависят от размеров типов, порядка байтов или компилятора, может вести себя на целевой платформе иначе; именно поэтому `analyze`
  оставляет на C код, работающий с железом.

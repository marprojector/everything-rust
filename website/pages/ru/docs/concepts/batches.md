# Пакеты и горячие пути

```sh
everything-rust bridge <repo> <unit> --batch fn:param    # или: everything-rust refresh <crate> --batch fn:param
```

`--batch` генерирует класс, который принимает значения `param` один раз и хранит их в Rust: `new FnBatch(items)` (TS, Python, Java), `Mod::FnBatch.new(items)` (Ruby), `NewFnBatch(items)` (Go). На каждый запрос `run(<other args>)` возвращает все результаты одним массивом, а `rank(<other args>, min)` возвращает индексы элементов, лучшие первыми. Он работает на всех ядрах, а ошибки совпадают с ошибками оригинала. Пакеты получают все языки, кроме C.

Порт, вызываемый по разу на каждый элемент, платит за мост за каждый элемент и проигрывает JIT. Выигрывает
перенос цикла: `profile` находит его, а `--batch` генерирует класс, который принимает элементы один раз
и выполняет функцию над всеми ними за вызов, на всех ядрах, с результатами в типизированных массивах.

```sh
everything-rust profile ../x18n -- node --experimental-strip-types $PWD/demo/x18n-search/search.ts .
# -> fuzzyScore: четверть всего прогона, вызывается на каждый ключ из `matched`: нужно пакетировать
everything-rust bridge ../x18n packages/core/src/fuzzy.ts --batch fuzzyScore:text
```

```js
const search = new FuzzyScoreBatch(keys)          // once
const order = search.rank(query, 0)               // per keystroke: indexes, best first
```

Структура `FuzzyScoreIndex` в `port.rs` заменяет цикл по умолчанию циклом, который подготавливает
элементы один раз и умеет ранжировать сам (`rank`): она хранит ключи в нижнем регистре с маской символов
для каждого, таблицу первой позиции каждого частого символа в каждом ключе (запрос из одной буквы занимает один
столбец) и совпадения последнего запроса (ввод `se` после `s` пересчитывает только то, что совпало с `s`). На
поиске в боковой панели x18n по 50,000 ключей, при вводе по букве, с идентичными результатами:

| | На запрос | против TS |
| --- | ---: | ---: |
| TS: `map(fuzzyScore)`, filter, sort | 10 ms | 1x |
| TS с тем же сужением, что и в индексе | 4.1-5.4 ms | 2x |
| Тот же порт, вызываемый на каждый ключ | - | 0.2-0.4x |
| `FuzzyScoreBatch`, индекс по умолчанию (4 ядра) | 5.1 ms | 1.7x |
| `FuzzyScoreBatch` с `FuzzyScoreIndex` (napi, 4 ядра) | 0.45-0.56 ms | **18-22x** |
| То же с wasm (один поток) | 0.95 ms | **11.5x** |

По сравнению с TS, выполняющим то же сужение, Rust всё равно быстрее в 7-12x (wasm в 5x). Превращайте возвращённые
индексы в ключи обычным циклом: `Array.from(order, i => keys[i])` обходился в 20x дороже, 0.4 ms.

Пакеты есть у каждого языка, и они обгоняют оригинал даже там, где порты с вызовом на каждый элемент проигрывают.
Та же работа на 4 ядрах, идентичные результаты и ошибки (бенчмарки в каждом каталоге demo):

| Язык | Нагрузка | Оригинал | Порт с вызовом на элемент против оригинала | Пакет против оригинала |
| --- | --- | ---: | ---: | ---: |
| TS | поиск x18n, 50,000 ключей | 10 ms | 0.2-0.4x | **20x** |
| Python | `slugify`, 20,000 строк | 98 ms | - | **17x** |
| Ruby | `slugify`, 20,000 строк | 110 ms | - | **12.7x** |
| Ruby | `shellescape` (stdlib), 50,000 смешанных значений | 88 ms | - | **11.8x** |
| Go | `Slugify`, 50,000 строк | 49 ms | 0.93x | **4x** |
| Java | `slugify`, 50,000 строк | 43 ms | 0.68x | **3x** |

Компилируемые оригиналы выигрывают меньше: работа на элемент и так быстрая, поэтому пакет выигрывает за счёт числа
ядер. Пакетные крейты выделяют память через mimalloc: с системным аллокатором пакет для Go был медленнее
одного потока. Демо: [`demo/x18n-search`](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-search/README.md).
## Как написать быстрый индекс

- Пусть вызывающий код строит пакет один раз, а не на каждый запрос. Отображайте возвращённые индексы обратно на элементы обычным циклом.
- Чтобы подготовить элементы один раз (нижний регистр, маски, таблицы позиций), определите `pub struct FnIndex` в `port.rs` с `new(items)` и `run(<other args>)`. Он должен давать тот же результат, что и функция, элемент за элементом.
- Когда ранжирование может пропускать работу, дайте индексу собственный `rank(<other args>, min)`. Он должен совпадать с ранжированием результатов функции: оценка от высокой к низкой, при равенстве в порядке элементов.
- Пакет умножает скорость порта на элемент на число ядер. Против компилируемых оригиналов (Go, Java) сам порт должен быть быстрым: обрабатывайте ASCII без таблиц Unicode, собирайте каждый результат в одной заранее выделенной `String`, избегайте промежуточных копий.
- В Go и Java закрывайте пакет, когда закончите (финализаторы служат лишь запасным вариантом).

# x18n

| Hedef | Ne çalıştı | Sonuç |
| --- | --- | --- |
| `packages/core`, 9 birim, 29 fonksiyon | analyze, bridge, record, diff, bench, shadow, gate | her gate geçiyor; 9,000+ kayıtlı vaka eşleşiyor; köprü üzerinden TS'ten daha yavaş ([rapor](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)) |
| `packages/builtins/src/formats/shared/`, 7 fonksiyon | aynı | 3,672/3,672 vaka eşleşiyor, bunların 960'ı deponun 40 gerçek dosyasından (YAML yerel ayarları, JSON, Markdown, TS) LF ve CRLF olarak oluşturuldu |
| deponun tamamı | analyze | 142 birim; `start_here` artık yalnızca köprülenebilir export'u olan birimleri listeliyor |

Araçta bulunan ve düzeltilenler:

- `analyze` önce format ayrıştırıcılarını öneriyordu, ama tek export'ları plugin fabrikalarıydı
  (`properties(): Plugin`). `analyze` artık köprülenebilir export'ları `bridge`'in uyguladığı kurallarla
  sayıyor ve hiç olmayan birimleri `start_here` dışında bırakıyor.
- Workspace paketlerinden (`@x18n/core`) import edilen tipler izlenmiyordu, bu yüzden `Plugin` veri gibi
  görünüyordu. Tip araması artık workspace paketlerini kaynaklarına kadar izliyor.
- `record`, çalışma zamanında `@x18n/core`'u import eden bir modülü çalıştıramıyordu: paketin derleme
  çıktısı yok. Resolve hook'u artık workspace paketlerini kaynaklarına eşliyor.
- Biçimlendirilmiş girdiler `text.ts` portunda gerçek bir hata (bir aralıkta Infinity), ardından NaN
  karşılaştırıcılarıyla V8'in sıralamasına bir sıra bağımlılığı buldu; `js::sort` artık V8'i yeniden üretiyor.

## Çekirdek, fonksiyon fonksiyon

x18n çekirdeğinin API değişikliği olmadan taşınabilen 29 fonksiyonunun tamamı everything-rust ile port edildi:
her gate geçiyor ve 7,925 kayıtlı vaka tam olarak eşleşiyor. Ardından `everything-rust bench`, portların JS'ten
çağrıldığı haliyle TS'ten daha yavaş olduğunu gösterdi, çünkü köprünün maliyeti yapılan işten fazla. Raporun
tamamı: [`demo/x18n-core`](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md). Ders araca işlendi: bir portu
yayına almadan önce `bench` ile ölçün.

## Arama, batch olarak

Yukarıdaki yaprak portlar çağrı başına ölçülmüştür. x18n'in kenar çubuğu aramasında (50,000 anahtar,
harf harf yazılarak) `everything-rust profile`, `fuzzyScore`'u çalışmanın yaklaşık dörtte biri olarak,
`matched` tarafından anahtar başına bir kez çağrılırken gösterdi ve `--batch fuzzyScore:text` önerdi. Üretilen
`FuzzyScoreBatch` anahtarları Rust'ta tutar; `port.rs` içindeki bir `FuzzyScoreIndex` onları bir kez UTF-16
olarak küçük harfe çevirir ve her anahtardaki kod birimlerinin 64 bitlik bir maskesini tutar, böylece
eşleşemeyecek anahtarların çoğu okunmadan atlanır. Sonuçlar her sorgu için TS hattıyla aynıdır:

| | Sorgu başına ms | TS'e göre |
| --- | ---: | ---: |
| TS hattı | 10 | 1x |
| Aynı daraltmayı yapan TS | 4.1-5.4 | 2x |
| Batch, varsayılan indeks (öğe başına port, 4 çekirdek) | 5.1 | 1.7x |
| `FuzzyScoreIndex` (maskeler) ile batch, napi, 4 çekirdek | 1.2 | 7x |
| Kendi kendine sıralayan `FuzzyScoreIndex` ile batch, napi, 4 çekirdek | 0.45-0.56 | 18-22x |
| Aynısı, wasm, 1 thread | 0.95 | 11.5x |

7x'ten 20x'e geçiş: 1.2 ms'nin 0.4 ms'si benchmark'ın kendi `Array.from(order, i =>
keys[i])` çağrısıydı (düz bir döngü 0.02 ms tutar). Geri kalanı, indeksin kendi kendine sıralamasına
izin vermekten geldi: yeni sorgu son sorguyu genişlettiğinde yalnızca son sorgunun eşleşmelerini yeniden
puanlar (`s` ile eşleşmeyen bir anahtar `se` ile eşleşemez), tek harfli sorguları ilk konumlar tablosundan
okur, ASCII anahtarları bayt olarak puanlar ve tam sayı puanları bir counting sort ile sıralar. Callgrind,
30 baytlık anahtarlarda kütüphane çağrılarının (`memchr`, `memcmp`) düz döngülerden daha pahalı olduğunu
gösterdi. Kazancın bir kısmı algoritmadan gelir, bu yüzden benchmark aynı daraltmayı yapan TS'i de
çalıştırır: Rust ondan 7-12x daha hızlıdır (wasm 5x).

Diğer dillerde aynı desen, orijinallere karşı (4 çekirdek, aynı sonuçlar ve hatalar):

| Dil | İş yükü | Orijinal | Çağrı başına portun orijinale oranı | Batch'in orijinale oranı |
| --- | --- | ---: | ---: | ---: |
| Python | fixture `slugify`, 20,000 string | 98 ms | - | 17x |
| Ruby | fixture `slugify`, 20,000 string | 110 ms | - | 12.7x |
| Ruby | `Shellwords.shellescape`, 50,000 karışık değer | 88 ms | - | 11.8x |
| Go | fixture `Slugify`, 50,000 string | 49 ms | 0.93x | 3.3-4.1x |
| Java | fixture `slugify`, 50,000 string | 43 ms | 0.68x | 3.0x |

Go batch'i ilk başta tek thread'den daha yavaş çalıştı: port öğe başına bellek ayırıyor ve glibc'nin
ayırıcısı Go süreci içindeki thread'leri sıraya sokuyordu. Batch crate'leri artık mimalloc kullanıyor.
shellescape batch'i ayrıca çağrı başına kaydın kaçırdığı bir port hatası buldu: Ruby sembolleri
(`shellescape(:sym)`) JSON işaretleri olarak geri dönüyordu. Portta düzeltildi.

Go ve Java ardından 2.5x ve 1.7x'ten 4x ve 3x'e çıktı. Batch içinde zamanın yarısı iş değildi: sonuçlar
tek bir thread'de birleştirilip serbest bırakılıyordu, Go onları ikinci kez kopyalıyordu ve Java her string
için modified UTF-8 üzerinden bir JNI çağrısı yapıyordu. String sonuçları artık tüm çekirdeklerde Go'nun
kendi buffer'ına ya da tek bir Java `char[]`'ına yazılarak toplu olarak geri dönüyor. Diğer yarısı portlardı:
tek thread'de Rust `slugify` Go'nunkinden ancak biraz hızlı ve Java'nın JIT'inden daha yavaştı. ASCII'yi
tablo araması ve ara string olmadan küçük harfe çevirmek bunu düzeltti; Java portu son sigma kuralını,
yalnızca `Σ` içeren boşlukla ayrılmış parçayı bir bütün olarak küçük harfe çevirerek korur.
Çağrı başına Go portu 0.73x'ten 0.93x'e, Java portu 0.46x'ten 0.68x'e çıktı.

# 基准测试

```sh
everything-rust bench <crate>
```

`bench` 在原实现和构建好的 Rust 模块上为录制用例计时（包含桥接开销），返回各行数据和一个附带建议的结论：上线、把较慢的函数留在源语言中，或者迁移更大的单元。加速比低于 1 表示按调用方的调用方式，移植版更慢。`--min-ms` 设置每个函数每一侧的最短测量时间（默认 200）。

请遵循结论。不要在不说明的情况下上线一个让调用方变慢的移植版。

## 为什么移植版可能更慢

逐条数据调用一次的移植版，每条数据都要跨一次桥接层。决定因素是：

- **解释型原实现（Python、Ruby）**：调用 Rust 的开销约为 100-300 ns，而 Rust 代码比解释器快得多，所以即使是小函数也能获益。
- **编译型原实现（Go、经过 JIT 的 Java）**：原实现的叶子函数只需 4-90 ns；单次 cgo 调用本身就要约 80 ns，带字符串的 JNI 调用更多。这些语言只有在一次调用完成大量工作时才能获益：把函数和它的调用方一起迁移。
- **C**：没有跨边界开销；Rust 代码直接与 C 代码对比。

在真实代码上逐次调用的测量结果（[六种语言](/docs/real-world/six-languages)）：

| 语言 | Rust 相比原实现（`bench`，几何平均） | 结论 |
| --- | --- | --- |
| Ruby | **快 4.4 倍**（各函数为 3.6-7x） | 上线 |
| Python | **快 1.35 倍**（大多数调用为 1.5-1.9x） | 上线 |
| C | 0.87x：ctype 快 1.1-1.4 倍，glibc 精心调优的 `strtod`、`strspn`、`strcmp` 为 0.5-0.7x | 优化，或保留较慢的函数 |
| Java | 0.18x | 迁移更大的单元 |
| Go | 0.04x | 迁移更大的单元 |

x18n core 中所有能在不改 API 的情况下迁移的 29 个函数都已迁移：每个门禁都通过，7,925 条录制用例完全一致，而 `bench` 显示从 JS 调用时移植版比 TS 更慢，因为桥接开销比实际工作还大（[报告](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)）。在录制用例上，vercel/ms 逐次调用的速度是 0.56x（[案例研究](/docs/real-world/vercel-ms)）。

## 真正能赢的：迁移循环

`profile` 找到热点函数外层的循环，`--batch` 把整个循环迁到 Rust，在全部核心上运行。见[批处理与热点路径](/docs/concepts/batches)。

::: tip 在空闲的机器上测量
请在空闲的机器上运行 `bench`，运行两次，并在每个公布的数字旁注明硬件和核心数。
:::

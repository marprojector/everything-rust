# vercel/ms

[vercel/ms](https://github.com/vercel/ms)(스타 5.5k, 커밋 `4ff48ce`)는 `"2 days"`를
밀리초로 바꾸고 그 반대도 합니다. 대부분의 Node 프로젝트가 어떤 의존성을 통해 이를 끌어옵니다. everything-rust 1.5.1로
처음부터 끝까지 포팅했으며, crate는
[`demo/real-world/vercel-ms-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/vercel-ms-rs)에 있습니다.

| 단계 | 결과 |
| --- | --- |
| `analyze` | 유닛 1개(`src/index.ts`), ready, 준비도 96 |
| `bridge --kind napi` | `ms`, `parse`, `parseStrict`, `format` 브리지됨, TS에 남긴 것 없음 |
| `record --from-tests -- jest` | 케이스 975개: 생성된 케이스, 함정 케이스, vercel/ms의 Jest 테스트 167개에서 수집한 호출 340개(첫 포트는 테스트에서 손으로 복사한 입력 149개를 사용) |
| 포트 | TS 184줄에 대해 Rust 200줄, 배치마다 `options`를 한 번 읽는 `FormatIndex` 포함 |
| `diff` | 첫 빌드에서 784/784 일치, 수집한 호출을 더해 975/975 |
| `gate` | 통과(fmt, clippy, 테스트, 오류 경로, 크기, 동작) |
| `bench`, 호출당 | 기록된 케이스에서 0.56x(처음에는 0.39x): 일반 문자열에 대한 `parse`는 79 ns로 JS와 같지만, 엣지 케이스와 발생한 오류는 브리지를 거치며 여전히 더 비쌈 |
| 배치, `parse` x100,000 | JS 11.8 ms, Rust 0.65 ms: **18x**, 문자열을 한 번 넘기는 비용을 포함하면 3.4x(문자열을 이어 붙여 넘기기 전에는 2.1x) |
| 배치, `format` x100,000 | JS 2.1 ms, 전달 비용 포함 Rust 2.5 ms: **0.8x**(처음에는 0.2x), `format(x, { long: true })`는 1.2x |

포트가 정확히 맞춰야 했던 부분, 모두 기록된 케이스나 함정 케이스가 잡아냈습니다:

- `u` 플래그가 없는 `/.../i`는 ASCII 문자만 대소문자를 무시하지만 Rust의 `regex`는 유니코드 전체를 무시합니다. 그래서
  `"1 ſ"`(긴 s)와 켈빈 기호가 초로 파싱될 뻔했습니다. 포트는 단위를 ASCII로만,
  직접 매칭합니다.
- `Math.round`는 0.5를 올림합니다(`-2.5`는 `-2`). Rust의 `round`는 0에서 먼 쪽으로 반올림합니다.
- `${n}`은 `1e+21`, `5e-324`를 출력하고 `-0`은 `0`으로 출력합니다. 포트는 JS의 숫자-문자열 변환을 재현합니다.
  첫 버전에는 동점 처리 버그(`25.728225708007812`가 `...813`으로 출력)도 있었는데, ms의
  정수 출력에서는 나타나지 않는 경우입니다.
- `str.length`는 UTF-16 유닛을 세므로, 100자 제한에서 이모지는 두 글자로 셉니다.

도구에서 발견해 고친 것: 구조화된 매개변수(`format`의
`options`)를 가진 napi 배치 메서드가 컴파일되지 않았습니다. 생성된 바인딩이 `serde_json::Value`를 받았는데, napi는
`serde-json` 기능 없이는 이를 변환할 수 없기 때문입니다. 이제 배치 클래스가 있는 crate는 이 기능을 켭니다.

이 포팅에서 도구로 다시 가져온 것:

- 생성된 `js.rs`에 `js::number_to_string`과 `js::math_round`가 있으며, 무작위 double 20,000개로
  Node와 대조해 검증했습니다. 포트는 자체 사본 대신 이를 사용합니다. `number_to_string`은
  serde_json의 출력기에서 숫자를 가져옵니다: 정수는 `format!`보다 5배, 소수는 3배 빠릅니다.
- napi 배치는 문자열 항목을 UTF-16 끝 오프셋과 함께 이어 붙인 문자열 하나로, 숫자 항목을
  `Float64Array` 하나로 보내고, 문자열 결과는 이어 붙여 반환합니다(`index.cjs`가 `slice`로 나눔).
  항목마다 JS 값 하나를 쓰는 것보다 문자열은 2배, 숫자는 20배 빠릅니다. `new Batch(items)`와
  `run()`의 형태는 그대로입니다.
- `analyze`는 `Math.round`, `toFixed`, 그리고 `s`나 `k`를 언급하는 `u` 없는 `/i` 정규식을 표시하고,
  각각에 대한 안내를 붙입니다.
- 호출 비용이 줄었습니다: napi에서 모든 동기 함수는 napi 인자 없이 바이너리 와이어를 거치고
  (인자 하나가 약 55 ns, 호출 전체는 22 ns), 함수마다 JS 래퍼가 두 개가 아니라 하나이며,
  `serde_json::Value` 매개변수는 어떤 형태든 태그가 붙은 값으로 건너가고, 오류는
  와이어 버퍼에 담겨 돌아옵니다. 호출당 `parse`가 121 ns에서 79 ns로 줄었습니다.
- `record --from-tests`는 테스트 입력을 손으로 복사하는 일을 대신합니다: 테스트가 실행되는 동안
  스위트가 하는 각 호출을 기록하며, 수집 코드는 커버리지에서 제외합니다(ms는 100%를 강제함).

판정: `ms`는 좋은 포팅 결과이지만 나쁜 속도 개선 대상입니다. 기록된 모든 케이스에서 정확하며,
프로그램이 많은 기간 값을 한 번에 파싱할 때만 더 빠릅니다.

# 벤치

```sh
everything-rust bench <crate>
```

`bench`는 원본과 빌드된 Rust 모듈에서 브리지 비용을 포함해 기록된 케이스의 실행 시간을 재고, 결과 행과 조언이 담긴 판정을 반환합니다: 배포하기, 느린 함수는 원본 언어에 남기기, 또는 더 큰 유닛을 포팅하기. 속도 향상이 1 미만이면 호출하는 쪽이 호출하는 방식으로는 포트가 더 느리다는 뜻입니다. `--min-ms`는 함수와 측별 최소 측정 시간을 정합니다(기본값 200).

판정을 따르세요. 호출하는 쪽을 느리게 만드는 포트를 아무 말 없이 배포하지 마세요.

## 포트가 더 느릴 수 있는 이유

항목마다 한 번씩 호출되는 포트는 항목마다 브리지 비용을 치릅니다. 결과를 가르는 요인:

- **인터프리터 언어 원본(Python, Ruby)**: Rust 호출 비용은 약 100-300 ns이고 Rust 코드는 인터프리터보다 훨씬 빠르므로, 작은 함수도 이득을 봅니다.
- **컴파일 언어 원본(Go, JIT 이후의 Java)**: 원본 리프 함수는 4-90 ns가 걸립니다. cgo 호출 하나만으로도 약 80 ns가 들고, 문자열을 넘기는 JNI 호출은 그보다 더 듭니다. 이런 언어는 한 번의 호출이 많은 일을 할 때만 이득을 봅니다. 함수를 호출자와 함께 포팅하세요.
- **C**: 경계를 넘는 비용이 없습니다. Rust 코드를 C 코드와 직접 비교합니다.

실제 코드에서 호출당 측정한 결과([여섯 가지 언어](/docs/real-world/six-languages)):

| 언어 | 원본 대비 Rust (`bench`, 기하 평균) | 판정 |
| --- | --- | --- |
| Ruby | **4.4배 빠름** (함수별 3.6-7x) | 배포 |
| Python | **1.35배 빠름** (대부분의 호출에서 1.5-1.9x) | 배포 |
| C | 0.87x: ctype은 1.1-1.4x 빠름, glibc가 최적화한 `strtod`, `strspn`, `strcmp`는 0.5-0.7x | 최적화하거나 느린 것은 유지 |
| Java | 0.18x | 더 큰 유닛 포팅 |
| Go | 0.04x | 더 큰 유닛 포팅 |

x18n core에서 API 변경 없이 옮길 수 있는 함수 29개를 모두 포팅했습니다: 모든 게이트가 통과하고 기록된 케이스 7,925개가 정확히 일치했지만, `bench`는 JS에서 호출할 때 포트가 TS보다 느리다는 것을 보여 주었습니다. 브리지 비용이 실제 작업보다 크기 때문입니다([보고서](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)). vercel/ms는 기록된 케이스에서 호출당 0.56x였습니다([사례 연구](/docs/real-world/vercel-ms)).

## 이기는 방법: 루프 옮기기

`profile`이 핫 함수를 감싸는 루프를 찾고, `--batch`가 그 루프 전체를 Rust로 옮겨 모든 코어에서 실행합니다. [배치와 핫 패스](/docs/concepts/batches)를 참고하세요.

::: tip 조용한 머신에서 측정하세요
`bench`는 다른 작업이 없는 조용한 머신에서 두 번 실행하고, 공개하는 모든 수치 옆에 하드웨어와 코어 수를 적으세요.
:::

# x18n

| 目標 | 執行了什麼 | 結果 |
| --- | --- | --- |
| `packages/core`，9 個單元，29 個函式 | analyze、bridge、record、diff、bench、shadow、gate | 每個 gate 都通過；9,000+ 個已錄製案例一致；透過橋接時比 TS 慢（[報告](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)） |
| `packages/builtins/src/formats/shared/`，7 個函式 | 同上 | 3,672/3,672 個案例一致，其中 960 個是以儲存庫中 40 個真實檔案（YAML 語系檔、JSON、Markdown、TS）建構，包含 LF 與 CRLF |
| 整個儲存庫 | analyze | 142 個單元；`start_here` 現在只列出具有可橋接匯出的單元 |

在工具中發現並已修正的問題：

- `analyze` 建議先移植格式解析器，但它們唯一的匯出是外掛工廠
  （`properties(): Plugin`）。`analyze` 現在會以 `bridge` 所套用的規則計算可橋接的匯出，
  並將沒有任何可橋接匯出的單元排除在 `start_here` 之外。
- 從 workspace 套件（`@x18n/core`）匯入的型別沒有被追蹤，所以 `Plugin` 看起來
  像是資料。型別查找現在會沿著 workspace 套件追蹤到它們的原始碼。
- `record` 無法在執行期執行匯入 `@x18n/core` 的模組：該套件沒有建置
  輸出。resolve hook 現在會將 workspace 套件對應到它們的原始碼。
- 有形狀的輸入在 `text.ts` 的移植版本中找到一個真正的錯誤（範圍中的 Infinity），接著又找到對 V8 在
  NaN 比較函式下排序結果的順序依賴；`js::sort` 現在會重現 V8 的行為。
## 核心，逐一函式

x18n 核心中所有 29 個能在不改變 API 的情況下搬移的函式都已用 everything-rust 移植：
每個 gate 都通過，7,925 個已錄製的案例完全一致。接著 `everything-rust bench` 顯示從 JS 呼叫時，
這些移植版本比 TS 慢，因為橋接的成本比實際工作還高。完整報告：
[`demo/x18n-core`](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)。這個教訓已內建在工具中：出貨移植版本之前，
先用 `bench` 量測。
## 搜尋，以批次方式

上述的末端移植是以單次呼叫量測的。在 x18n 的側邊欄搜尋上（50,000 個 key，逐字母
輸入），`everything-rust profile` 顯示 `fuzzyScore` 約佔執行時間的四分之一，由 `matched` 對每個 key
呼叫一次，並建議使用 `--batch fuzzyScore:text`。自動產生的 `FuzzyScoreBatch` 會把
key 保留在 Rust 中；`port.rs` 中的 `FuzzyScoreIndex` 會一次把它們轉為小寫的 UTF-16，並為每個 key 保留一個記錄其程式碼單元的 64 位元
遮罩，所以大多數不可能符合的 key 會在未讀取的情況下被略過。每個查詢的結果
都與 TS 流程完全相同：

| | 每次查詢 ms | 相對於 TS |
| --- | ---: | ---: |
| TS 流程 | 10 | 1x |
| 使用相同縮減方式的 TS | 4.1-5.4 | 2x |
| 批次，預設索引（逐項目移植，4 核心） | 5.1 | 1.7x |
| 批次搭配 `FuzzyScoreIndex`（遮罩），napi，4 核心 | 1.2 | 7x |
| 批次搭配自行排名的 `FuzzyScoreIndex`，napi，4 核心 | 0.45-0.56 | 18-22x |
| 相同，wasm，1 個執行緒 | 0.95 | 11.5x |

從 7x 到 20x 的那一步：在 1.2 ms 中，有 0.4 ms 是基準測試自己的 `Array.from(order, i =>
keys[i])`（一般迴圈只需 0.02 ms）。其餘來自讓索引自行排名：
當新查詢延伸上一次查詢時，它只會重新計分上一次查詢的符合結果（不符合
`s` 的 key 不可能符合 `se`），從首次出現位置表讀取單一字母的查詢，以位元組計分
ASCII key，並以計數排序對整數分數排序。Callgrind 顯示在 30 位元組的 key 上，
函式庫呼叫（`memchr`、`memcmp`）的成本比一般迴圈還高。部分的提升
來自演算法，所以基準測試也執行了使用相同縮減方式的 TS：Rust 比它快 7-12x
（wasm 為 5x）。

其他語言中相同的模式，與原始版本相比（4 核心，結果與錯誤
完全相同）：

| 語言 | 工作負載 | 原始版本 | 單次呼叫移植相對於原始版本 | 批次相對於原始版本 |
| --- | --- | ---: | ---: | ---: |
| Python | fixture `slugify`，20,000 個字串 | 98 ms | - | 17x |
| Ruby | fixture `slugify`，20,000 個字串 | 110 ms | - | 12.7x |
| Ruby | `Shellwords.shellescape`，50,000 個混合值 | 88 ms | - | 11.8x |
| Go | fixture `Slugify`，50,000 個字串 | 49 ms | 0.93x | 3.3-4.1x |
| Java | fixture `slugify`，50,000 個字串 | 43 ms | 0.68x | 3.0x |

Go 的批次一開始比單一執行緒還慢：移植版本對每個項目配置記憶體，而 glibc 的配置器
在 Go 行程中讓執行緒變成序列化執行。批次 crate 現在使用 mimalloc。shellescape 批次
也找到一個單次呼叫錄製沒抓到的移植錯誤：Ruby 的 symbol（`shellescape(:sym)`）回傳時
變成了它們的 JSON 標記。已在移植版本中修正。

之後 Go 與 Java 從 2.5x 與 1.7x 提升到 4x 與 3x。在批次內部，有一半的時間並不是
實際工作：結果在單一執行緒上合併與釋放，Go 又複製了一次，而 Java
透過 modified UTF-8 對每個字串做一次 JNI 呼叫。字串結果現在會整批回傳，使用所有核心
寫入 Go 自己的緩衝區或一個 Java `char[]` 中。另一半則是移植版本本身：在單一
執行緒上，Rust 的 `slugify` 只比 Go 的快一點點，而且比 Java 的 JIT 還慢。處理 ASCII 小寫轉換時
不查表也不使用中間字串，就解決了這個問題；Java 的移植版本為了保留詞尾 sigma 規則，
只把含有 `Σ` 的那段以空白分隔的片段整段轉為小寫。
以單次呼叫而言，Go 的移植版本從 0.73x 提升到 0.93x，Java 的從 0.46x 提升到 0.68x。

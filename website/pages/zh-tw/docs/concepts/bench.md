# 基準測試

```sh
everything-rust bench <crate>
```

`bench` 會在原始版本與建置好的 Rust 模組上（包含橋接）為已錄製的案例計時，並回傳各列結果與附帶建議的結論：出貨、將較慢的函式留在來源語言，或移植更大的單元。加速比低於 1 代表以呼叫端的呼叫方式而言，移植版本比較慢。`--min-ms` 設定每個函式在每一側的最短量測時間（預設 200）。

請遵循結論。不要在沒有說明的情況下出貨一個讓呼叫端變慢的移植版本。

## 為什麼移植版本可能比較慢

每個項目呼叫一次的移植版本，每個項目都要付出一次橋接成本。決定因素如下：

- **直譯式的原始版本（Python、Ruby）**：呼叫 Rust 的成本約為 100-300 ns，而 Rust 程式碼比直譯器快得多，所以即使是小函式也能勝出。
- **編譯式的原始版本（Go、經過 JIT 的 Java）**：原始的末端函式只需 4-90 ns；光是一次 cgo 呼叫就要約 80 ns，帶字串的 JNI 呼叫更多。這些語言只有在一次呼叫做大量工作時才會受益：請將函式連同它的呼叫端一起移植。
- **C**：沒有跨越成本；Rust 程式碼直接與 C 程式碼比較。

在真實程式碼上以單次呼叫量測（[六種語言](/docs/real-world/six-languages)）：

| 語言 | Rust 相對於原始版本（`bench`，幾何平均） | 結論 |
| --- | --- | --- |
| Ruby | **快 4.4x**（每個函式 3.6-7x） | 出貨 |
| Python | **快 1.35x**（大多數呼叫 1.5-1.9x） | 出貨 |
| C | 0.87x：ctype 快 1.1-1.4x，glibc 調校過的 `strtod`、`strspn`、`strcmp` 為 0.5-0.7x | 最佳化，或保留較慢的函式 |
| Java | 0.18x | 移植更大的單元 |
| Go | 0.04x | 移植更大的單元 |

x18n 核心中所有 29 個能在不改變 API 的情況下搬移的函式都已移植：每個 gate 都通過，7,925 個已錄製的案例完全一致，而 `bench` 顯示從 JS 呼叫時，這些移植版本比 TS 慢，因為橋接的成本比實際工作還高（[報告](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)）。vercel/ms 在其已錄製的案例上，單次呼叫為 0.56x（[案例研究](/docs/real-world/vercel-ms)）。

## 勝出的方法：搬移迴圈

`profile` 會找出熱點函式外圍的迴圈，而 `--batch` 會將整個迴圈搬進 Rust，並使用所有核心。請參閱[批次與熱路徑](/docs/concepts/batches)。

::: tip 在安靜的機器上量測
請在安靜的機器上執行 `bench`，執行兩次，並在每個公開的數字旁註明硬體與核心數。
:::

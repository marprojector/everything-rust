# ベンチマーク

```sh
everything-rust bench <crate>
```

`bench` は記録ケースを元の実装とビルドした Rust モジュールでブリッジ込みで計測し、結果の行とアドバイス付きの判定を返します: 出荷する、遅い関数は元の言語に残す、またはより大きなユニットを移植する、のいずれかです。速度向上が 1 未満なら、呼び出し元からの呼び方では移植版の方が遅いということです。`--min-ms` で関数ごと・実装ごとの最小計測時間を設定します（デフォルトは 200）。

判定に従ってください。呼び出し元を遅くする移植版を、それを明示せずに出荷してはいけません。

## 移植版が遅くなる理由

要素ごとに 1 回呼ばれる移植版は、要素ごとに 1 回ブリッジのコストを払います。決め手となるのは次の点です:

- **インタプリタ型の元の実装（Python、Ruby）**: Rust への呼び出しは約 100-300 ns で、Rust のコードはインタプリタよりはるかに速いので、小さな関数でも速くなります。
- **コンパイル型の元の実装（Go、JIT 後の Java）**: 元の末端関数は 4-90 ns で済みます。cgo の呼び出し 1 回だけで約 80 ns、文字列を伴う JNI の呼び出しはさらにかかります。これらの言語では、1 回の呼び出しで多くの処理をする場合にのみ速くなります: 関数をその呼び出し元ごと移植してください。
- **C**: 境界を越えるコストはありません。Rust のコードを C のコードと直接比較します。

実際のコードで呼び出しごとに計測した結果（[6 つの言語](/docs/real-world/six-languages)）:

| 言語 | 元の実装に対する Rust（`bench`、幾何平均） | 判定 |
| --- | --- | --- |
| Ruby | **4.4 倍高速**（関数ごとに 3.6-7 倍） | 出荷 |
| Python | **1.35 倍高速**（ほとんどの呼び出しで 1.5-1.9 倍） | 出荷 |
| C | 0.87 倍: ctype は 1.1-1.4 倍高速、glibc のチューニング済み `strtod`、`strspn`、`strcmp` は 0.5-0.7 倍 | 最適化するか、遅いものは残す |
| Java | 0.18 倍 | より大きなユニットを移植 |
| Go | 0.04 倍 | より大きなユニットを移植 |

API を変えずに移せる x18n のコアの 29 関数すべてを移植しました: すべてのゲートに合格し、7,925 件の記録ケースが完全に一致しましたが、`bench` によると JS から呼ぶ場合は移植版の方が TS より遅いことがわかりました。ブリッジのコストが処理そのものより大きいためです（[レポート](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)）。vercel/ms は記録ケース全体で呼び出しごとに 0.56 倍でした（[ケーススタディ](/docs/real-world/vercel-ms)）。

## 速くなる方法: ループを移す

`profile` はホットな関数を囲むループを見つけ、`--batch` はそのループ全体を Rust に移して全コアで実行します。[バッチとホットパス](/docs/concepts/batches)を参照してください。

::: tip 静かなマシンで計測する
`bench` は負荷のかかっていないマシンで 2 回実行し、公開するすべての数値にハードウェアとコア数を併記してください。
:::

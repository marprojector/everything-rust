# vercel/ms

[vercel/ms](https://github.com/vercel/ms)（5.5k スター、コミット `4ff48ce`）は `"2 days"` をミリ秒に変換し、
その逆も行います。ほとんどの Node プロジェクトは何らかの依存関係を通じてこれを取り込んでいます。everything-rust 1.5.1 で
エンドツーエンドに移植しました。クレートは
[`demo/real-world/vercel-ms-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/vercel-ms-rs) にあります。

| ステップ | 結果 |
| --- | --- |
| `analyze` | 1 ユニット（`src/index.ts`）、準備完了、準備度 96 |
| `bridge --kind napi` | `ms`、`parse`、`parseStrict`、`format` をブリッジ。TS に残したものはなし |
| `record --from-tests -- jest` | 975 ケース: 生成されたもの、トラップ、そして vercel/ms の 167 個の Jest テストから取得した 340 件の呼び出し（最初の移植版では、そこから手でコピーした 149 個の入力を使用） |
| 移植 | TS の 184 行に対して 200 行の Rust。バッチごとに `options` を一度だけ読む `FormatIndex` を含む |
| `diff` | 最初のビルドで 784/784 が一致。取得した呼び出しを含めて 975/975 |
| `gate` | 合格（fmt、clippy、テスト、エラーパス、サイズ、挙動） |
| `bench`、呼び出しごと | 記録ケース全体で 0.56 倍（当初は 0.39 倍）: 通常の文字列に対する `parse` は 79 ns で JS と同等ですが、エッジケースと投げられるエラーはブリッジ経由ではまだコストが高い |
| バッチ、`parse` x100,000 | JS 11.8 ms、Rust 0.65 ms: **18 倍**。文字列の一度きりの受け渡しを含めると 3.4 倍（文字列を連結して渡す前は 2.1 倍） |
| バッチ、`format` x100,000 | JS 2.1 ms、受け渡しを含めて Rust 2.5 ms: **0.8 倍**（当初は 0.2 倍）。`format(x, { long: true })` は 1.2 倍 |

移植版が正しく扱わなければならなかったこと。すべて記録ケースまたはトラップで捕まりました:

- `u` フラグのない `/.../i` は ASCII 文字だけを大文字小文字同一視しますが、Rust の `regex` は Unicode で同一視するので、
  `"1 ſ"`（長い s）やケルビン記号が秒としてパースされてしまうところでした。移植版は単位を
  手で、ASCII のみで照合します。
- `Math.round` は 0.5 を切り上げます（`-2.5` は `-2`）。Rust の `round` はゼロから遠い方に丸めます。
- `${n}` は `1e+21`、`5e-324` を出力し、`-0` には `0` を出力します。移植版は JS の数値から文字列への変換を再現します。
  最初のバージョンには、ms の整数出力では決して到達しない、同値の丸めのバグ（`25.728225708007812` が `...813` と表示される）もありました。
- `str.length` は UTF-16 ユニットで数えるので、100 文字の上限では絵文字を 2 文字と数えます。

ツールで見つかり、修正されたもの: 構造化された引数（`format` の
`options`）を持つ napi のバッチメソッドがコンパイルできませんでした。生成されたバインディングが `serde_json::Value` を受け取っていましたが、napi は
`serde-json` 機能なしではそれを変換できないためです。バッチクラスを持つクレートでは現在この機能が有効になります。

この移植からツールに取り込まれたもの:

- 生成される `js.rs` には `js::number_to_string` と `js::math_round` があり、20,000 個のランダムな倍精度浮動小数点数で
  Node と照合済みです。移植版は独自のコピーの代わりにそれらを使います。`number_to_string` は
  serde_json のプリンターから桁を取得します: 整数では `format!` より 5 倍、小数では 3 倍高速です。
- napi のバッチは、文字列の要素を UTF-16 の終了オフセット付きで 1 つの連結文字列として、数値の要素を
  1 つの `Float64Array` として送り、文字列の結果を連結して返します（`index.cjs` が `slice` で分割します）:
  要素ごとに 1 つの JS 値を渡す場合と比べ、文字列で 2 倍、数値で 20 倍高速です。`new Batch(items)` と
  `run()` の形は変わりません。
- `analyze` は `Math.round`、`toFixed`、そして `s` や `k` を含む `u` なしの `/i` 正規表現を、
  それぞれのガイダンス付きで指摘します。
- 呼び出しのコストが下がりました: napi では、すべての同期関数が napi の引数なしでバイナリワイヤを通ります
  （引数 1 つで約 55 ns、呼び出し全体で 22 ns）。JS のラッパーは関数ごとに 2 つではなく 1 つになり、
  `serde_json::Value` の引数は任意の形のタグ付き値として境界を越え、エラーはワイヤのバッファで返ってきます。
  `parse` の呼び出しごとの時間は 121 ns から 79 ns になりました。
- `record --from-tests` は、テストの入力を手でコピーする作業を置き換えます: テストの実行中にスイートが行う各呼び出しを
  記録し、取得用のコードはカバレッジから除外されます（ms は 100% を強制しています）。

結論: `ms` は移植としては良好ですが、高速化の対象としては不向きです。すべての記録ケースで正しく、
プログラムが多数の期間を一度にパースするときだけ速くなります。

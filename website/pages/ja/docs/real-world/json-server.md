# json-server

[json-server](https://github.com/typicode/json-server)（75k スター、MIT、コミット `89a34a4`、
1.0.0-beta.15）は JSON ファイルから REST API を提供します: Node、tinyhttp、lowdb で作られています。これは
アプリ全体のフロー（`app record`、`front-door`、`wire`、`lift`）でエンドツーエンドに移植した最初のアプリで、
結果は Node サーバーと同じ応答を返す 1 つの Rust バイナリです。すべては
[`demo/real-world/json-server-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/json-server-rs) にあります。

| ステップ | 結果 |
| --- | --- |
| `analyze --whole-app` | サーバー、9 ユニット（7 つが準備完了、2 つが要注意）、置き換える依存関係 13 個（tinyhttp、lowdb、sirv、eta、milliparsec、dot-prop、sort-on、inflection など） |
| `app record --http` | 514 ケース: `--inputs` で与えた 268 リクエスト（すべてのルートとメソッド、where 演算子、ソート、ページネーション、埋め込み、CORS のプリフライト、静的ファイルと範囲指定、29 個の不正な JSON ボディ、`/__proto__` などのプロトタイプ名、不正なエスケープ）と 245 のトラップ。それぞれ 2 回記録し、ランダムな ID は `[..]` のまま |
| `front-door` | フォールバック率 99.8% で 513/514。失敗した 1 件は URL 内の生の `ü` で、Node は 400 を返し、プロキシは再エンコードする |
| ユニット | `where-operators` 207、`parse-where` 289、`matches-where` 1,346、`paginate` 853 ケース（json-server 自身のテストからの呼び出しを含む）。`service` 461 と `app` 243 は、Service の呼び出しと実際の HTTP リクエストを実行する 2 つの小さなアダプター経由。6 つすべてが `gate` に合格 |
| `wire` | まず読み取り: フォールバック率 22.6% で 514/514。書き込みには Node が応答し、Rust は Node が書いたファイルを再読み込み。次にすべてのルート: フォールバック率 0% で 514/514 |
| `lift` | 純粋な Rust バイナリ（5.3 MB）、514/514。`bin.ts` のコマンドライン（ヘルプ、バージョン、ファイルのチェック、起動時のバナー）は手で移植 |

リフト後のユニットにはバインディングがないので、各クレートの `tests/recorded.rs` が移植版に対して
記録ケースをリプレイします: 3,399 件すべてが `cargo test` で実行されます。

移植版が正しく扱わなければならなかったこと。すべて記録ケースで捕まりました:

- tinyhttp のルーターは 1 回だけディスパッチするのではありません: `next()` のたびに、最後のミドルウェアが書き換えた URL で
  すべてのミドルウェアとルートを再度照合し、`HEAD` に対してはすべてのルートを実行します。そのため
  `HEAD /posts` は GET のハンドラーを実行し、次に POST のハンドラーを実行して、POST の 400 を返します。`//posts` は CORS
  ヘッダとボディパーサーをスキップします。移植版はそのループをそのまま実行します。
- milliparsec は POST、PUT、PATCH、DELETE のすべてのボディを型に関係なく JSON としてパースし、不正な
  ものは V8 のメッセージ付きの 500 になります: `Expected double-quoted property name in JSON at position 7
  (line 1 column 8)`、`Unexpected token 'x', ..."bbbbbbb": x}" is not valid JSON`。移植版は
  UTF-16 ユニットでの位置も含めて V8 のパーサーのエラーを再現します。3,806 個の不正な入力で Node と照合済みです。
- ソートは `localeCompare`（ICU）を使います。これは ICU4X のコレーターで行い、3,000 組で確認済みです。
  `Number()`、`JSON.stringify`（`1e+21`、整数のキーが先）、Node の 2 つのクエリ文字列パーサー
  （`é%E9` を WHATWG とは異なる方法でデコードする）、エラーメッセージ付きの dot-prop、埋め込みのための inflection
  （`person` と `people`）は、それぞれ `json-server-js` で Node と照合しています。
- `db.data[name]` は `Object.prototype` を読みます: `/__proto__` は `{}` を、`/constructor` は空の
  200 を返し、`PATCH /__proto__` はデータベースのプロトタイプを置き換え、それは後の検索から見えます。
- Node の HTTP パーサーは、生の非 ASCII のターゲットと未知のメソッドに対して 400 を返して接続を閉じます。

json-server で見つかったこと: 自身の書き込みのたびに、ファイル監視がファイルを再読み込みします。その再読み込みが
終わる前に次のリクエストが書き込むと、再読み込みがその書き込みを消してしまうことがあります: サーバーの応答と同じ速さで送った
最初の記録では、201 が返った POST が後の読み取りに現れませんでした。`app record --pace 50` はリクエストの間に待機し、
ケースはその方法で記録されています。移植版は他の誰かがファイルを変更したときだけ再読み込みするので、
その書き込みを失いません: これは意図的な違いです。

ベンチマーク: Apple M4（10 コア、16 GB）、macOS 27.3、Node 24.15.0 で、`tsc` が npm 向けにビルドした
`lib/bin.js` を実行、Rust バイナリは `--release` でビルド。両方ともループバック上で同じ
データベースのコピーを提供し、`ab -k` がウォームアップ後に同じリクエストを行ごとに 20,000 件送ります（大きなデータベースでの
遅い埋め込みは 40 件）。2 回実行し、それぞれ 1 分間のロードアベレージが 3 未満の状態で開始しました。
セルは 1 回目 / 2 回目の 1 秒あたりのリクエスト数です。スクリプトは [`bench/bench.py`](https://github.com/marprojector/everything-rust/blob/main/demo/real-world/json-server-rs/bench/bench.py)
です。

差が小さいケース: 1 接続で 10,000 件の投稿リスト全体を読む場合（1.2 倍: どちらも 1.5 MB の JSON の出力に
時間を費やす）、大きなデータベースへの書き込み（1.1 から 1.2 倍: どちらも書き込みのたびに 3.6 MB のファイル全体を
書き直し、Rust は lowdb と同様にキューに入った書き込みをまとめる）、そして 1 接続でのソート済みタイトル検索（1.4 倍）です。
大きな差は並行処理（Node のプロセスにはないもの）と、埋め込み（json-server はすべての投稿について
すべてのコメントをフィルタリングするが、移植版はリクエストごとにコメントを一度だけインデックスし、結果は同じ）から来ています。

最初にリフトしたバイナリは、大きなデータベースでは Node より遅いものでした（リスト全体で 1 秒あたり 33 対 298
リクエスト、書き込みで 39 対 217）。プロファイリングで、順に次のことがわかりました: `TCP_NODELAY` がない
（大きなレスポンスはそれぞれ遅延 ACK を約 40 ms 待っていた）、書き込みのたびに `$schema` を追加するためにデータベース全体を
クローンしていた、出力前にリストのすべての要素をクローンしていた、すべてのリクエストで 1 つのロックを使っていた、
10,000 個の要素それぞれについて `item.id` を SipHash でハッシュしていた。すべて修正済みで、3,399 件の
ユニットのケースと 514 件の HTTP ケースは各変更の後に合格しています。

ツールで見つかり、修正されたもの:

- 状態を書き込むサーバーは、同じ開始状態から 2 回記録できませんでした:
  `--fresh <path>` は現在、ケースと一緒に保存したスナップショットから、起動のたびにデータベース（と `public/`）を新しい作業
  ディレクトリにコピーします。`--arg` はすべてのビルドに元の実装の引数を渡します。
  `--pace` は上記のとおりです。
- `bridge` は `paginate<T>(items: T[])` を TS に残していました（関数を含む何にでもジェネリック）。
  `--as-json T` はこれを JSON 値としてブリッジします。
- パラメータ付きのフロントドアのルートは、ユニットがリクエストを見る前に、`/posts/%E0` に対して axum 自身の 400 を
  返していました。パラメータは現在 URI から読み取られます。
- `lift` はワイヤリングしたユニットだけをステージし、パスで依存しているクレートはステージしていませんでした。また
  `cargo fmt --check` が拒否する `lib.rs` を書いていました。どちらも修正済みです。
- 生成するサーバーが `TCP_NODELAY` を設定していませんでした: 2 回に分けて書かれたレスポンスは
  クライアントの遅延 ACK を約 40 ms 待っていました。現在は設定しています。

カバーしないもの: JSON5 のデータベース（バイナリはそう伝えて終了します）、100 KiB のボディ上限
（Node の上限はボディが 64 KiB の読み取りでどう届くかに依存します。移植版は完全な読み取りを前提とします）、孤立サロゲートを含む文字列
（U+FFFD になります）、そして `1e400` というデータベースの値（Node は次の再読み込みまで `Infinity` を
メモリに保持します。移植版は `null` を保存し、これはファイルに書かれる値と同じです）。

# x18n

| 対象 | 実行したもの | 結果 |
| --- | --- | --- |
| `packages/core`、9 ユニット、29 関数 | analyze、bridge、record、diff、bench、shadow、gate | すべてのゲートに合格。9,000 件以上の記録ケースが一致。ブリッジ経由では TS より遅い（[レポート](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)） |
| `packages/builtins/src/formats/shared/`、7 関数 | 同上 | 3,672/3,672 ケースが一致。そのうち 960 件はリポジトリの実際の 40 ファイル（YAML のロケール、JSON、Markdown、TS）から LF と CRLF で作成 |
| リポジトリ全体 | analyze | 142 ユニット。`start_here` は現在、ブリッジ可能なエクスポートを持つユニットだけを挙げる |

ツールで見つかり、修正されたもの:

- `analyze` はフォーマットのパーサーを最初に推奨していましたが、そのエクスポートはプラグインのファクトリー
  （`properties(): Plugin`）だけでした。`analyze` は現在、`bridge` が適用するルールでブリッジ可能なエクスポートを数え、
  それが 1 つもないユニットを `start_here` から除外します。
- ワークスペースのパッケージ（`@x18n/core`）からインポートされた型がたどられていなかったため、`Plugin` が
  データに見えていました。型の検索は現在、ワークスペースのパッケージをそのソースまでたどります。
- `record` は実行時に `@x18n/core` をインポートするモジュールを実行できませんでした: そのパッケージにはビルド
  出力がありません。resolve フックは現在、ワークスペースのパッケージをそのソースに対応付けます。
- 形を整えた入力が `text.ts` の移植版で実際のバグ（範囲内の Infinity）を見つけ、次に NaN を返す比較関数を使った
  V8 のソートへの順序依存を見つけました。`js::sort` は現在 V8 を再現します。
## コア、関数ごと

API を変えずに移せる x18n のコアの 29 関数すべてを everything-rust で移植しました:
すべてのゲートに合格し、7,925 件の記録ケースが完全に一致しました。その後 `everything-rust bench` により、JS から呼ぶ場合は
移植版の方が TS より遅いことがわかりました。ブリッジのコストが処理そのものより大きいためです。完全なレポート:
[`demo/x18n-core`](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)。この教訓は組み込まれています: 移植版を出荷する前に
`bench` で計測してください。
## 検索をバッチで

上記の末端関数の移植版は呼び出しごとに計測しています。x18n のサイドバー検索（50,000 キー、1 文字ずつ
入力）では、`everything-rust profile` が、`fuzzyScore` が実行時間の約 4 分の 1 を占め、`matched` からキーごとに 1 回
呼ばれていることを示し、`--batch fuzzyScore:text` を提案しました。生成された `FuzzyScoreBatch` は
キーを Rust 側に保持します。`port.rs` の `FuzzyScoreIndex` はキーを一度だけ小文字化して UTF-16 にし、各キーに含まれる
コードユニットの 64 ビットマスクを保持するので、一致しえないキーのほとんどは読まずにスキップされます。結果は
すべてのクエリで TS のパイプラインと同一です:

| | 1 クエリあたりの ms | TS 比 |
| --- | ---: | ---: |
| TS のパイプライン | 10 | 1x |
| 同じ絞り込みをした TS | 4.1-5.4 | 2x |
| バッチ、デフォルトのインデックス（要素ごとに移植版、4 コア） | 5.1 | 1.7x |
| `FuzzyScoreIndex`（マスク）付きのバッチ、napi、4 コア | 1.2 | 7x |
| 自身でランク付けする `FuzzyScoreIndex` 付きのバッチ、napi、4 コア | 0.45-0.56 | 18-22x |
| 同じものを wasm、1 スレッドで | 0.95 | 11.5x |

7 倍から 20 倍への段階: 1.2 ms のうち 0.4 ms はベンチマーク自身の `Array.from(order, i =>
keys[i])` でした（単純なループなら 0.02 ms）。残りは、インデックスに自分でランク付けさせたことによるものです:
新しいクエリが直前のクエリを延長する場合は直前のクエリに一致したものだけを再スコアリングし（`s` に一致しないキーは
`se` にも一致しえない）、1 文字のクエリは最初の位置のテーブルから読み、ASCII のキーはバイトとしてスコアリングし、
整数のスコアを計数ソートで並べます。Callgrind によると、30 バイトのキーでは
ライブラリ呼び出し（`memchr`、`memcmp`）の方が単純なループよりコストが高いことがわかりました。向上の一部は
アルゴリズムによるものなので、ベンチマークでは同じ絞り込みをした TS も実行しています: Rust はそれより 7-12 倍高速です
（wasm は 5 倍）。

他の言語でも同じパターンを、元の実装に対して（4 コア、結果とエラーは同一）:

| 言語 | ワークロード | 元の実装 | 呼び出しごとの移植版 vs 元の実装 | バッチ vs 元の実装 |
| --- | --- | ---: | ---: | ---: |
| Python | フィクスチャの `slugify`、20,000 文字列 | 98 ms | - | 17x |
| Ruby | フィクスチャの `slugify`、20,000 文字列 | 110 ms | - | 12.7x |
| Ruby | `Shellwords.shellescape`、50,000 個の混在値 | 88 ms | - | 11.8x |
| Go | フィクスチャの `Slugify`、50,000 文字列 | 49 ms | 0.93x | 3.3-4.1x |
| Java | フィクスチャの `slugify`、50,000 文字列 | 43 ms | 0.68x | 3.0x |

Go のバッチは当初シングルスレッドより遅く実行されました: 移植版が要素ごとにメモリを確保し、glibc のアロケーターが
Go プロセス内のスレッドを直列化していたためです。バッチのクレートは現在 mimalloc を使います。shellescape のバッチは、
呼び出しごとの記録では見逃されていた移植版のバグも見つけました: Ruby のシンボル（`shellescape(:sym)`）が
JSON のマーカーとして返ってきていたのです。移植版で修正しました。

その後 Go と Java は 2.5 倍と 1.7 倍から 4 倍と 3 倍になりました。バッチ内では、時間の半分は処理そのものではありませんでした:
結果が 1 つのスレッドで連結・解放され、Go はそれをもう一度コピーし、Java は修正 UTF-8 を通じて文字列ごとに
1 回の JNI 呼び出しを行っていました。文字列の結果は現在まとめて返され、全コアで Go 自身のバッファか Java の 1 つの `char[]` に
書き込まれます。残りの半分は移植版でした: 1 スレッドでは、Rust の `slugify` は Go よりわずかに速いだけで、Java の JIT より
遅かったのです。ASCII をテーブル検索なしで、中間文字列も使わずに小文字化することでそれを解決しました。Java の移植版は、
`Σ` を含む空白区切りの部分だけを丸ごと小文字化することで語末シグマのルールを保っています。
呼び出しごとでは、Go の移植版は 0.73 倍から 0.93 倍に、Java のものは 0.46 倍から 0.68 倍になりました。

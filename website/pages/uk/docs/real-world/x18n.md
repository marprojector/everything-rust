# x18n

| Ціль | Що запускали | Результат |
| --- | --- | --- |
| `packages/core`, 9 модулів, 29 функцій | analyze, bridge, record, diff, bench, shadow, gate | кожен gate проходить; 9,000+ записаних випадків збігаються; через міст повільніше за TS ([звіт](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md)) |
| `packages/builtins/src/formats/shared/`, 7 функцій | те саме | 3,672/3,672 випадків збігаються, 960 з них побудовано з 40 реальних файлів репозиторію (локалі YAML, JSON, Markdown, TS), у LF і CRLF |
| увесь репозиторій | analyze | 142 модулі; `start_here` тепер перелічує лише модулі з експортами, які можна з'єднати мостом |

Знайдено в інструменті й виправлено:

- `analyze` рекомендував першими парсери форматів, але їхніми єдиними експортами є фабрики плагінів
  (`properties(): Plugin`). Тепер `analyze` рахує експорти, які можна з'єднати мостом, за тими самими правилами, що
  застосовує `bridge`, і не включає модулі без таких експортів у `start_here`.
- Типи, імпортовані з пакетів робочого простору (`@x18n/core`), не відстежувалися, тож `Plugin` виглядав
  як дані. Пошук типів тепер іде пакетами робочого простору до їхнього вихідного коду.
- `record` не міг запустити модуль, що імпортує `@x18n/core` під час виконання: пакет не має результатів
  збірки. Хук резолвінгу тепер зіставляє пакети робочого простору з їхнім вихідним кодом.
- Вхідні дані заданої форми знайшли справжній баг у порті `text.ts` (Infinity в діапазоні), а потім залежність
  від порядку в сортуванні V8 з компараторами, що повертають NaN; `js::sort` тепер відтворює V8.
## Ядро, функція за функцією

Усі 29 функцій ядра x18n, які можна перенести без зміни API, було портовано за допомогою everything-rust:
кожен gate проходить і 7,925 записаних випадків збігаються точно. Потім `everything-rust bench` показав, що порти
повільніші за TS при виклику з JS, бо міст коштує більше за саму роботу. Повний звіт:
[`demo/x18n-core`](https://github.com/marprojector/everything-rust/blob/main/demo/x18n-core/README.md). Урок вбудовано в інструмент: вимірюйте через `bench`, перш ніж
випускати порт.
## Пошук як пакет

Наведені вище порти листкових функцій виміряно на виклик. На пошуку в бічній панелі x18n (50,000 ключів, введення по
літері) `everything-rust profile` показав, що `fuzzyScore` займає приблизно чверть прогону і викликається один раз для кожного ключа з
`matched`, і запропонував `--batch fuzzyScore:text`. Згенерований `FuzzyScoreBatch` тримає
ключі в Rust; `FuzzyScoreIndex` у `port.rs` один раз переводить їх у нижній регістр в UTF-16 і зберігає 64-бітну
маску кодових одиниць кожного ключа, тож більшість ключів, які не можуть збігтися, пропускаються без читання. Результати
ідентичні конвеєру TS для кожного запиту:

| | ms на запит | проти TS |
| --- | ---: | ---: |
| Конвеєр TS | 10 | 1x |
| TS з тим самим звуженням | 4.1-5.4 | 2x |
| Пакет, стандартний індекс (порт на елемент, 4 ядра) | 5.1 | 1.7x |
| Пакет з `FuzzyScoreIndex` (маски), napi, 4 ядра | 1.2 | 7x |
| Пакет з `FuzzyScoreIndex`, що ранжує сам, napi, 4 ядра | 0.45-0.56 | 18-22x |
| Те саме, wasm, 1 потік | 0.95 | 11.5x |

Крок від 7x до 20x: з 1.2 ms 0.4 ms припадало на власний `Array.from(order, i =>
keys[i])` бенчмарку (звичайний цикл коштує 0.02 ms). Решта прийшла від того, що індексу дали ранжувати самому:
він переоцінює лише збіги останнього запиту, коли новий запит його продовжує (ключ, що не
збігається з `s`, не може збігтися з `se`), читає однолітерні запити з таблиці перших позицій, оцінює
ключі ASCII як байти і впорядковує цілочисельні оцінки сортуванням підрахунком. Callgrind показав, що
бібліотечні виклики (`memchr`, `memcmp`) коштують більше за звичайні цикли на 30-байтних ключах. Частина виграшу
припадає на алгоритм, тож бенчмарк також запускає TS з тим самим звуженням: Rust у 7-12x швидший
за нього (wasm 5x).

Той самий шаблон в інших мовах, проти оригіналів (4 ядра, ідентичні результати і
помилки):

| Мова | Навантаження | Оригінал | Порт з поодинокими викликами проти оригіналу | Пакет проти оригіналу |
| --- | --- | ---: | ---: | ---: |
| Python | `slugify` з фікстури, 20,000 рядків | 98 ms | - | 17x |
| Ruby | `slugify` з фікстури, 20,000 рядків | 110 ms | - | 12.7x |
| Ruby | `Shellwords.shellescape`, 50,000 різнотипних значень | 88 ms | - | 11.8x |
| Go | `Slugify` з фікстури, 50,000 рядків | 49 ms | 0.93x | 3.3-4.1x |
| Java | `slugify` з фікстури, 50,000 рядків | 43 ms | 0.68x | 3.0x |

Пакет Go спершу працював повільніше за один потік: порт виділяє пам'ять на кожен елемент, і алокатор glibc
серіалізував потоки всередині процесу Go. Пакетні крейти тепер використовують mimalloc. Пакет shellescape
також знайшов баг порту, який пропустив запис з поодинокими викликами: символи Ruby (`shellescape(:sym)`) поверталися
як їхня JSON-позначка. Виправлено в порті.

Потім Go і Java перейшли від 2.5x і 1.7x до 4x і 3x. Усередині пакета половина часу йшла не
на роботу: результати об'єднувалися і звільнялися в одному потоці, Go копіював їх ще раз, а Java
робила один виклик JNI на рядок через модифікований UTF-8. Тепер рядкові результати повертаються гуртом, записані
на всіх ядрах у власний буфер Go або в один `char[]` Java. Друга половина припадала на самі порти: в одному
потоці `slugify` на Rust був ледь швидшим за Go і повільнішим за JIT Java. Зниження регістру ASCII
без пошуку в таблицях і без проміжного рядка це виправило; порт для Java зберігає
правило кінцевої сигми, знижуючи регістр лише цілого фрагмента між пробілами, що містить `Σ`.
На виклик порт Go перейшов від 0.73x до 0.93x, порт Java від 0.46x до 0.68x.

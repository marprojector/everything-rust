# Fuse.js

[Fuse.js](https://github.com/krisk/Fuse) (20k зірок, близько 20 мільйонів завантажень з npm на тиждень,
коміт `edf2fb6`) є бібліотекою нечіткого пошуку за незліченними пошуковими полями. Портовано за допомогою
everything-rust 1.6 (ще не випущено); крейт лежить у [`demo/real-world/fuse-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/fuse-rs).

`analyze` помістив кожну теку `src/` в один цикл імпортів, тож Fuse не можна портувати файл за файлом.
Натомість порт бере шлях, на який пошук витрачає свій час: адаптер на 54 рядки
(`adapter/relevance.ts`) експортує власну оцінку Fuse для одного рядка зі списку рядків, побудовану з
`BitapSearch`, нормування поля і `computeScoreSingle` у Fuse. Саме цю функцію пошук по
50,000 рядках виконує 50,000 разів. `bridge --batch relevance:text` тримає рядки в Rust і
виконує пошук по всіх них, на всіх ядрах.

| Крок | Результат |
| --- | --- |
| адаптер | ранжування адаптера дорівнює `new Fuse(list).search(q)` на 81 запиті та наборі параметрів ще до будь-якого Rust |
| `record --inputs` | 3,414 випадків: заголовки з власних фікстур Fuse, не-ASCII, емодзі, шаблони довші за 32 одиниці, кожен підтримуваний параметр і параметри неправильного типу (відхилені, 149 випадків) |
| порт | 673 рядки Rust замість 839 рядків Fuse, які він заміщує |
| `diff` | 3,414/3,414 збігаються з першої збірки |
| `gate` | проходить |
| заміна | `withRust(Fuse)` відповідає на пошуки в списку рядків у Rust і передає все інше Fuse; повертає результати, побайтово ідентичні Fuse, на 360 пошуках (12 наборів параметрів, 15 запитів, з `limit` і без) |

Час пошуку на запит, Apple M4 (10 ядер), Node 24, результати перевірено на ідентичність перед вимірюванням:

| Список | Fuse.js | Rust | Прискорення |
| ---: | ---: | ---: | ---: |
| 1,000 рядків | 1.9 ms | 0.1 ms | 18x |
| 10,000 рядків | 19.1 ms | 0.7 ms | 27 to 30x |
| 50,000 рядків | 91.2 ms | 2.8 ms | **32x** |
| 50,000 рядків, одне ядро | 92.0 ms | 17.5 ms | 5.3x |

Що порт мав зробити правильно:

- Bitap працює на 32-бітних цілих JS: `1 << 31` від'ємне, а `(1 << 31) - 1` є double, який
  стає `2147483647` при наступному зсуві. Порт зберігає ці значення такими, як вони є в JS.
- Текст індексується в кодових одиницях UTF-16, тож емодзі займає дві позиції, як і у Fuse.
- `ignoreDiacritics` це NFD плюс список діапазонів комбінованих знаків і кілька окремо виписаних літер
  (`ł`, `ß`, `ı`); порт використовує той самий список.
- `String.prototype.trim` вирішує, які рядки Fuse пропускає: пробільні символи JS, а не
  `char::is_whitespace` з Rust (який включає U+0085 і не включає U+FEFF).

Знайдено в інструменті й виправлено: пакетні крейти, чиї елементи були рядками, а результати ні,
отримували невикористаний хелпер і не проходили `clippy -D warnings`; а перевірка розміру в `gate` рахувала лише
адаптер (54 рядки, тож у 12.5x "завеликий") замість файлів Fuse, які він імпортує.

Що не охоплено: списки об'єктів з `keys`, розширений і токенний пошук, логічні запити,
`includeMatches`, власні `sortFn` чи `getFn`. Заміна передає їх Fuse без змін.
Прискорення потребує, щоб список лишався в Rust між пошуками; його побудова коштує приблизно стільки ж, скільки
власний індекс Fuse (3.4 ms проти 2.8 ms для 50,000 рядків).

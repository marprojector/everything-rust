# json-server

[json-server](https://github.com/typicode/json-server) (75k зірок, MIT, коміт `89a34a4`,
1.0.0-beta.15) надає REST API з файлу JSON: Node, tinyhttp і lowdb. Це перший цілий
застосунок, портований від початку до кінця через процес для цілого застосунку (`app record`, `front-door`, `wire`, `lift`):
результатом є один бінарник Rust, що відповідає так само, як сервер на Node. Усе лежить у
[`demo/real-world/json-server-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/json-server-rs).

| Крок | Результат |
| --- | --- |
| `analyze --whole-app` | сервер, 9 модулів (7 готові, 2 із застереженням), 13 залежностей для заміни (tinyhttp, lowdb, sirv, eta, milliparsec, dot-prop, sort-on, inflection...) |
| `app record --http` | 514 випадків: 268 запитів, заданих через `--inputs` (кожен маршрут і метод, оператори where, сортування, пагінація, вкладення, CORS preflight, статичні файли і діапазони, 29 некоректних тіл JSON, `/__proto__` та інші імена прототипу, погані escape-послідовності) і 245 пасток; кожен записано двічі, випадкові ідентифікатори лишено як `[..]` |
| `front-door` | 513/514 при 99.8% fallback; промах це сирий `ü` в URL, на який Node відповідає 400, а проксі перекодовує його |
| модулі | `where-operators` 207, `parse-where` 289, `matches-where` 1,346, `paginate` 853 випадки (включно з викликами з власних тестів json-server); `service` 461 і `app` 243 через два невеликі адаптери, що виконують виклики Service і справжні HTTP-запити; `gate` проходить на всіх шести |
| `wire` | спершу читання: 514/514 при 22.6% fallback, Node відповідає на записи, а Rust перечитує файл, записаний Node; потім кожен маршрут: 514/514 при 0% |
| `lift` | чистий бінарник Rust (5.3 MB), 514/514; командний рядок `bin.ts` портовано вручну (довідка, версія, перевірки файлу, банер при запуску) |

Після lift модулі не мають прив'язок, тож `tests/recorded.rs` кожного крейта відтворює його
записані випадки на порті: усі 3,399 запускаються через `cargo test`.

Що порт мав зробити правильно, усе це впіймали записані випадки:

- Маршрутизатор tinyhttp не диспетчеризує один раз: після кожного `next()` він знову зіставляє всі middleware і
  маршрути, з URL, який переписав останній middleware, і запускає кожен маршрут для `HEAD`. Тож
  `HEAD /posts` запускає обробник GET, потім обробник POST, і відповідає 400 від POST; `//posts` пропускає заголовки CORS
  і парсер тіла. Порт виконує цей цикл як є.
- milliparsec розбирає кожне тіло POST, PUT, PATCH і DELETE як JSON, хоч якого воно типу, а погане
  дає 500 з повідомленням V8: `Expected double-quoted property name in JSON at position 7
  (line 1 column 8)`, `Unexpected token 'x', ..."bbbbbbb": x}" is not valid JSON`. Порт
  відтворює помилки парсера V8, включно з позиціями в одиницях UTF-16; перевірено проти Node на
  3,806 некоректних вхідних даних.
- Сортування використовує `localeCompare` (ICU), реалізоване через колатор ICU4X і перевірене на 3,000 парах;
  `Number()`, `JSON.stringify` (`1e+21`, цілочисельні ключі першими), два парсери query-рядків Node
  (які декодують `é%E9` інакше, ніж WHATWG), dot-prop з його повідомленнями про помилки та inflection
  для вкладень (`person` і `people`) кожне перевірено проти Node у `json-server-js`.
- `db.data[name]` читає `Object.prototype`: `/__proto__` відповідає `{}`, `/constructor` порожнім
  200, а `PATCH /__proto__` замінює прототип бази даних, що бачать подальші звернення.
- HTTP-парсер Node відповідає 400 і закриває з'єднання на сирих не-ASCII цілях і невідомих методах.

Знайдено в json-server: після кожного власного запису його спостерігач за файлами перечитує файл. Коли
наступний запит пише до завершення цього перечитування, перечитування може стерти цей запис: у першому
записі, надісланому так швидко, як відповідав сервер, був POST із відповіддю 201, якого подальші читання не
показали. `app record --pace 50` чекає між запитами, і випадки записано саме так. Порт
перечитує файл лише тоді, коли його змінив хтось інший, тож не втрачає цей запис: навмисна
відмінність.

Бенчмарк: Apple M4 (10 ядер, 16 GB), macOS 27.3, Node 24.15.0 запускає `lib/bin.js` у тому вигляді, як
його збирає `tsc` для npm, бінарник Rust зібрано з `--release`. Обидва обслуговують копію тієї самої
бази даних на loopback; `ab -k` надсилає однакові запити, 20,000 на рядок (40 для повільного вкладення на
великій базі) після прогріву. Два прогони, кожен запущено при середньому навантаженні за 1 хвилину нижче 3;
у клітинках прогін 1 / прогін 2 у запитах на секунду. [`bench/bench.py`](https://github.com/marprojector/everything-rust/blob/main/demo/real-world/json-server-rs/bench/bench.py)
є скриптом.

Де розрив малий: одне з'єднання, що читає весь список з 10,000 постів (1.2x: обидва витрачають
час на друк 1.5 MB JSON), записи у велику базу (від 1.1 до 1.2x: обидва переписують увесь
файл на 3.6 MB при кожному записі, а Rust об'єднує записи в черзі, як це робить lowdb), і відсортований пошук
за заголовком на одному з'єднанні (1.4x). Великий виграш дає конкурентність, якої процес Node
не має, і вкладення, де json-server фільтрує кожен коментар для кожного поста (порт
індексує коментарі один раз на запит, з тим самим результатом).

Перший бінарник після lift був повільнішим за Node на великій базі (33 проти 298 запитів на
секунду для всього списку, 39 проти 217 для записів). Профілювання знайшло, по черзі: відсутність
`TCP_NODELAY` (кожна велика відповідь чекала близько 40 ms на відкладений ACK), клонування всієї бази даних
для додавання `$schema` перед кожним записом, клонування кожного елемента списку перед друком, одне блокування
на всі запити і хешування `item.id` через SipHash для кожного з 10,000 елементів. Усе виправлено; 3,399
випадків модулів і 514 HTTP-випадків проходять після кожної зміни.

Знайдено в інструменті й виправлено:

- Сервер, що записує свій стан, не можна було записати двічі з того самого старту:
  `--fresh <path>` тепер копіює базу даних (і `public/`) у свіжу робочу теку при кожному
  запуску, зі знімка, що зберігається разом із випадками; `--arg` дає кожній збірці аргументи оригіналу;
  `--pace` описано вище.
- `bridge` лишав `paginate<T>(items: T[])` у TS (генерик над будь-чим, включно з функціями);
  `--as-json T` з'єднує його мостом як значення JSON.
- Маршрути front door з параметрами відповідали власним 400 від axum на `/posts/%E0` ще до того, як
  модуль бачив запит; тепер параметри читаються з URI.
- `lift` готував лише підключений модуль, а не крейти, від яких той залежить за шляхом, і писав `lib.rs`,
  який відхиляв `cargo fmt --check`; обидва виправлено.
- Згенеровані ним сервери не встановлювали `TCP_NODELAY`: відповідь, записана двома частинами, чекала
  на відкладений ACK клієнта, близько 40 ms. Тепер вони його встановлюють.

Що не охоплено: бази даних JSON5 (бінарник про це повідомляє і завершується), обмеження тіла в 100 KiB
(у Node воно залежить від того, як тіло надходить читаннями по 64 KiB; порт припускає повні читання), рядки
з поодинокими сурогатами (вони стають U+FFFD) і значення `1e400` у базі (Node тримає `Infinity`
у пам'яті до наступного перечитування; порт зберігає `null`, що й потрапляє у файл).

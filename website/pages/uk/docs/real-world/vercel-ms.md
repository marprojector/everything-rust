# vercel/ms

[vercel/ms](https://github.com/vercel/ms) (5.5k зірок, коміт `4ff48ce`) перетворює `"2 days"` на
мілісекунди і назад; більшість проєктів на Node підтягують його через якусь залежність. Портовано від початку до кінця
за допомогою everything-rust 1.5.1; крейт лежить у
[`demo/real-world/vercel-ms-rs`](https://github.com/marprojector/everything-rust/tree/main/demo/real-world/vercel-ms-rs).

| Крок | Результат |
| --- | --- |
| `analyze` | 1 модуль (`src/index.ts`), готовий, готовність 96 |
| `bridge --kind napi` | `ms`, `parse`, `parseStrict` і `format` з'єднано мостом, жоден не лишився в TS |
| `record --from-tests -- jest` | 975 випадків: згенеровані, пастки і 340 викликів, захоплених із 167 тестів Jest у vercel/ms (перший порт використовував 149 вхідних значень, скопійованих із них вручну) |
| порт | 200 рядків Rust замість 184 рядків TS, включно з `FormatIndex`, що читає `options` один раз на пакет |
| `diff` | 784/784 збіглися з першої збірки; 975/975 із захопленими викликами |
| `gate` | проходить (fmt, clippy, тести, шляхи помилок, розмір, поведінка) |
| `bench`, на виклик | 0.56x на записаних випадках (0.39x спочатку): `parse` на звичайному рядку займає 79 ns, нарівні з JS, але граничні випадки і кинуті помилки через міст усе ще коштують більше |
| пакет, `parse` x100,000 | JS 11.8 ms, Rust 0.65 ms: **18x**; 3.4x з урахуванням одноразової передачі рядків (2.1x до того, як рядки почали передаватися об'єднаними) |
| пакет, `format` x100,000 | JS 2.1 ms, Rust 2.5 ms з передачею: **0.8x** (0.2x спочатку); `format(x, { long: true })` 1.2x |

Що порт мав зробити правильно, усе це впіймали записані випадки або пастки:

- `/.../i` без прапорця `u` згортає регістр лише для літер ASCII, а `regex` у Rust згортає Unicode, тож
  `"1 ſ"` (довга s) і знак Кельвіна розбиралися б як секунди. Порт розпізнає одиниці
  вручну, лише ASCII.
- `Math.round` округлює половини вгору (`-2.5` дає `-2`); `round` у Rust округлює від нуля.
- `${n}` друкує `1e+21`, `5e-324` і `0` для `-0`; порт відтворює перетворення чисел на рядок як у JS.
  Його перша версія також мала баг із рівними половинами (`25.728225708007812` друкувалося як `...813`), до якого
  цілочисельний вивід ms ніколи не доходить.
- `str.length` рахує одиниці UTF-16, тож обмеження в 100 символів рахує емодзі за два.

Знайдено в інструменті й виправлено: пакетний метод napi зі структурованим параметром (`options` у `format`)
не компілювався, бо згенерована прив'язка приймала `serde_json::Value`, який napi
не може перетворити без своєї можливості `serde-json`. Крейти з пакетними класами тепер її вмикають.

Що повернулося в інструмент із цього порту:

- Згенерований `js.rs` має `js::number_to_string` і `js::math_round`, перевірені проти Node на
  20,000 випадкових double; порт використовує їх замість власних копій. `number_to_string` бере
  свої цифри з принтера serde_json: у 5x швидше за `format!` для цілих, у 3x для дробів.
- Пакети napi надсилають рядкові елементи одним об'єднаним рядком із кінцевими зміщеннями UTF-16, числові елементи
  одним `Float64Array`, і повертають рядкові результати об'єднаними (`index.cjs` ділить їх через `slice`):
  у 2x швидше для рядків і в 20x для чисел, ніж одне значення JS на елемент. `new Batch(items)` і
  `run()` зберігають свою форму.
- `analyze` позначає `Math.round`, `toFixed` і регулярні вирази `/i` без `u`, що згадують `s` або `k`,
  з порадами щодо кожного.
- Виклики коштують менше: у napi кожна синхронна функція йде через бінарний wire без аргументів napi
  (аргумент коштує близько 55 ns, весь виклик 22 ns), одна обгортка JS на функцію замість
  двох, параметри `serde_json::Value` передаються як позначені значення будь-якої форми, а помилки повертаються
  в буфері wire. `parse` на виклик пришвидшився зі 121 до 79 ns.
- `record --from-tests` замінює ручне копіювання вхідних даних тестів: він записує кожен виклик, який робить набір тестів,
  під час їх виконання, а код захоплення виключено з покриття (ms вимагає 100%).

Вердикт: `ms` є добрим портом і поганою ціллю для прискорення. Правильний на кожному записаному випадку, швидший
лише тоді, коли програма розбирає багато тривалостей за раз.

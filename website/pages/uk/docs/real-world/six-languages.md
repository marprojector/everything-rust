# Реальний код шістьма мовами

everything-rust запустили від початку до кінця (analyze, bridge, record, port, diff, gate, bench) на реальному коді
кожною мовою, яку він підтримує. Код мав уже бути на цій машині: код, завантажений з
інтернету, не виконувався. Тому цілями є модулі стандартних бібліотек, що постачаються з
встановленими тулчейнами, а для Java і C, де на диску не знайшлося відповідного вихідного коду бібліотек, оракулом
за тонким фасадом слугують самі JDK і glibc.

Порти, записані випадки і додаткові вхідні дані лежать у [`demo/real-world`](https://github.com/marprojector/everything-rust/blob/main/demo/real-world/README.md).

| Мова | Код | Функції | Записані випадки | Результат |
| --- | --- | ---: | ---: | --- |
| Go | `path` зі стандартної бібліотеки Go 1.24 | 7 (+1 лишено) | 2,642 (542 з власних тестових таблиць Go) | 2,642/2,642, gate проходить |
| Ruby | `shellwords.rb` з Ruby 3.3 | 3 | 1,617 (446 кидають виняток) | 1,617/1,617, gate проходить |
| Python | `colorsys.py` з CPython 3.13 | 6 | 2,400 | 2,400/2,400, gate проходить |
| Java | JDK 21 за фасадом (`Integer`, `Long`, `Math`, `Double.toString`, `URLEncoder`, `Base64`, `toUpperCase`) | 11 | 4,492 (226 кидають виняток) | 4,492/4,492, gate проходить |
| C | glibc за фасадом (`strtol`, `atoi`, `strtod`, `strspn`, `strcmp`, ctype) | 9 | 1,860 (6 збоїв) | 1,859/1,859 після вилучення одного випадку з невизначеною поведінкою, gate проходить |
| C | aklomp/base64 (вбудований у runtime mypyc) | 0 з 7 | - | лише план: кожна функція приймає вихідні буфери або структуру стану |

## Швидкість

Перші мости для Python, Go, Ruby і Java передавали кожен аргумент і результат через текст JSON,
що коштувало в 10-50x більше за роботу в цих функціях. Їх перебудували так, щоб вони перетворювали
значення напряму. Тепер `bench` вимірює лише виклики (аргументи декодуються один раз, у процесі) і каже,
чи варто випускати.

| Мова | На виклик раніше | На виклик тепер | Rust проти оригіналу (`bench`, середнє геометричне) | Вердикт |
| --- | ---: | ---: | --- | --- |
| Ruby | 6.9-9.5 µs (Fiddle + JSON) | 0.36-1.15 µs (розширення magnus) | **у 4.4x швидше** (3.6-7x на функцію) | випускати |
| Python | 11.7 µs (JSON) | близько 0.3 µs (пряме перетворення PyO3) | **у 1.35x швидше** (1.5-1.9x на більшості викликів) | випускати |
| C | - | без перетину: пряме лінкування | 0.87x: ctype у 1.1-1.4x швидше, налаштовані в glibc `strtod`, `strspn`, `strcmp` 0.5-0.7x | оптимізувати або лишити повільніші |
| Java | близько 1.7 µs (JNI + JSON) | 30-800 ns (типізований JNI і бінарний wire) | 0.18x | портувати більші модулі |
| Go | 2.6 µs (cgo + JSON) | 0.11-0.42 µs (типізований cgo і бінарний wire) | 0.04x | портувати більші модулі |

Списки, мапи, структури і кілька результатів у Go і Java передаються через бінарний wire, згенерований для кожного
типу: `WordFreq` у Go (мапа) пришвидшився з 5.1 до 1.0 µs, `Midpoint` (структура) з 7.2 до 1.0 µs;
`frequencies` у Java (`Map`) з 8.4 до 1.0 µs, а `words` (`List<String>`) з 6.0 µs до
0.57 µs, у 1.39x швидше за саму Java.

TypeScript (ядро x18n, дев'ять модулів, 27 функцій на тих самих випадках): бінарний wire скоротив
вартість мосту в середньому на третину (`rangeContains` 3.6 -> 1.1 µs, `applyTextEdits` 10.4 -> 5.7
µs, `toWireRange` 5.0 -> 2.6 µs), а `buildTree` перейшов від рівності до у 2.0x швидше за TS. Решта
функцій є листками, які V8 виконує за 15-600 ns: у Rust вони досі повільніші, як і для Go та Java.

Що вирішує:

- **Інтерпретовані оригінали (Python, Ruby)**: виклик у Rust коштує близько 100-300 ns, а
  код Rust набагато швидший за інтерпретатор, тож виграють навіть маленькі функції.
- **Скомпільовані оригінали (Go, Java після JIT)**: листкова функція оригіналу займає 4-90 ns; один
  виклик cgo сам по собі коштує близько 80 ns, виклик JNI з рядками більше. Жоден міст не зробить функцію на 5 ns
  швидшою. Ці мови виграють лише тоді, коли один виклик робить багато роботи: портуйте функцію
  разом із кодом, що її викликає. `bench` так і каже.
- **C**: перетину межі немає; код Rust порівнюється з кодом C напряму, і результат
  є властивістю порту.

### Пакети: пошук у x18n

Наведені вище порти листкових функцій виміряно на виклик. На пошуку в бічній панелі x18n (50,000 ключів, введення по
літері) `everything-rust profile` показав, що `fuzzyScore` займає приблизно чверть прогону і викликається один раз для кожного ключа з
`matched`, і запропонував `--batch fuzzyScore:text`. Згенерований `FuzzyScoreBatch` тримає
ключі в Rust; `FuzzyScoreIndex` у `port.rs` один раз переводить їх у нижній регістр в UTF-16 і зберігає 64-бітну
маску кодових одиниць кожного ключа, тож більшість ключів, які не можуть збігтися, пропускаються без читання. Результати
ідентичні конвеєру TS для кожного запиту:

| | ms на запит | проти TS |
| --- | ---: | ---: |
| Конвеєр TS | 10 | 1x |
| TS з тим самим звуженням | 4.1-5.4 | 2x |
| Пакет, стандартний індекс (порт на елемент, 4 ядра) | 5.1 | 1.7x |
| Пакет з `FuzzyScoreIndex` (маски), napi, 4 ядра | 1.2 | 7x |
| Пакет з `FuzzyScoreIndex`, що ранжує сам, napi, 4 ядра | 0.45-0.56 | 18-22x |
| Те саме, wasm, 1 потік | 0.95 | 11.5x |

Крок від 7x до 20x: з 1.2 ms 0.4 ms припадало на власний `Array.from(order, i =>
keys[i])` бенчмарку (звичайний цикл коштує 0.02 ms). Решта прийшла від того, що індексу дали ранжувати самому:
він переоцінює лише збіги останнього запиту, коли новий запит його продовжує (ключ, що не
збігається з `s`, не може збігтися з `se`), читає однолітерні запити з таблиці перших позицій, оцінює
ключі ASCII як байти і впорядковує цілочисельні оцінки сортуванням підрахунком. Callgrind показав, що
бібліотечні виклики (`memchr`, `memcmp`) коштують більше за звичайні цикли на 30-байтних ключах. Частина виграшу
припадає на алгоритм, тож бенчмарк також запускає TS з тим самим звуженням: Rust у 7-12x швидший
за нього (wasm 5x).

Той самий шаблон в інших мовах, проти оригіналів (4 ядра, ідентичні результати і
помилки):

| Мова | Навантаження | Оригінал | Порт з поодинокими викликами проти оригіналу | Пакет проти оригіналу |
| --- | --- | ---: | ---: | ---: |
| Python | `slugify` з фікстури, 20,000 рядків | 98 ms | - | 17x |
| Ruby | `slugify` з фікстури, 20,000 рядків | 110 ms | - | 12.7x |
| Ruby | `Shellwords.shellescape`, 50,000 різнотипних значень | 88 ms | - | 11.8x |
| Go | `Slugify` з фікстури, 50,000 рядків | 49 ms | 0.93x | 3.3-4.1x |
| Java | `slugify` з фікстури, 50,000 рядків | 43 ms | 0.68x | 3.0x |

Пакет Go спершу працював повільніше за один потік: порт виділяє пам'ять на кожен елемент, і алокатор glibc
серіалізував потоки всередині процесу Go. Пакетні крейти тепер використовують mimalloc. Пакет shellescape
також знайшов баг порту, який пропустив запис з поодинокими викликами: символи Ruby (`shellescape(:sym)`) поверталися
як їхня JSON-позначка. Виправлено в порті.

Потім Go і Java перейшли від 2.5x і 1.7x до 4x і 3x. Усередині пакета половина часу йшла не
на роботу: результати об'єднувалися і звільнялися в одному потоці, Go копіював їх ще раз, а Java
робила один виклик JNI на рядок через модифікований UTF-8. Тепер рядкові результати повертаються гуртом, записані
на всіх ядрах у власний буфер Go або в один `char[]` Java. Друга половина припадала на самі порти: в одному
потоці `slugify` на Rust був ледь швидшим за Go і повільнішим за JIT Java. Зниження регістру ASCII
без пошуку в таблицях і без проміжного рядка це виправило; порт для Java зберігає
правило кінцевої сигми, знижуючи регістр лише цілого фрагмента між пробілами, що містить `Σ`.
На виклик порт Go перейшов від 0.73x до 0.93x, порт Java від 0.46x до 0.68x.

## Що знайшли прогони

### Баги в everything-rust, виправлені

- **Float змінювалися на один ULP** (прогін Java). Стандартний парсер float у `serde_json` не завжди
  округлює правильно. everything-rust спотворював записані вхідні дані під час читання, а згенеровані крейти
  спотворювали їх ще раз. 43 випадки `Double.toString` не проходили для правильного порту. Виправлено
  можливістю `float_roundtrip` у `serde_json` в everything-rust і в кожному згенерованому ним крейті (napi-rs,
  wasm і диспетчер JSON).
- **Збої C вбивали запис** (прогін C). Вхідні дані поза контрактом функції C (`isalpha(INT_MAX)`)
  спричиняють segfault у glibc. Тепер драйвер C запускає кожен випадок у дочірньому процесі через fork і записує
  `crash: SIGSEGV`; `diff` приймає там будь-яку поведінку порту, бо поведінка C невизначена.
- **`module_function :name` не розпізнавався** (прогін Ruby). `shellwords` оголошує свої функції модуля
  аргументами-символами після методів; експортер знав лише голу форму `module_function`.
  Тепер розпізнаються обидві форми.
- **Нетипізований код отримував сміттєві вхідні дані** (прогін Python). `colorsys` не має підказок типів, тож 1,709 з
  1,800 згенерованих випадків були `TypeError`. Тепер параметри без анотацій, що використовуються як числа (`r - g`,
  `max(r, g, b)`, `x < 1`), отримують тип `number`, у Python і Ruby: лишилося 94 помилки, усі справжні
  (`ZeroDivisionError`).
- **Int, передані як float, ніколи не записувалися** (прогін Python). Код на Python передає `1` так само часто, як
  `1.0`, а `colorsys` пропускає int далі (`hsv_to_rgb(0, 0, 7)` дорівнює `(7, 7, 7)`). Тепер під час запису
  цілі значення передаються як int у кожному четвертому випадку Python; це виявило 134 розбіжності в
  порті з типом `f64`.
- **Повідомлення з часів TypeScript**: "must stay in JS", "kept in TS", "characterization tests
  against the TS code" тепер називають мову оригіналу.
- **Повторно відкриті базові класи** (`class String` у `shellwords.rb`) тепер вважаються ризиком monkeypatching.

### Поведінка, якій має відповідати порт, знайдена через `diff`

Кожен рядок був розбіжністю в першому порті, яку впіймали записані випадки. Рядки, позначені *фікстура*,
походять з невеликих тестових проєктів у `tests/fixtures/`, написаних для кожної мови; решта з
наведених вище прогонів на реальному коді.

- Go `path.Clean`: `lazybuf` у Go читає байт за індексом запису після того, як той відступає назад, а не
  останній збережений байт (9 випадків, з власної тестової таблиці Go).
- *фікстура* `strings.ToLower` у Go і `downcase` у Ruby знижують регістр кожної руни окремо: `ΣΊΣΥΦΟΣ` стає `σίσυφοσ`,
  тоді як `to_lowercase` у Rust застосовує правило кінцевої сигми. Go також перетворює `İ` на `i`, а Rust
  дає `i̇`.
- *фікстура* Go ріже рядки за байтами; розріз посеред руни потрапляє в JSON як один U+FFFD на кожен байт.
- *фікстура* `slugify` у Ruby кидав `NoMethodError` для від'ємного `max` (`slug[0, -1]`
  дорівнює `nil`): баг в оригіналі, який порт має зберегти, або спершу треба виправити код, що викликає.
- *фікстура* `Array#sum` у Ruby використовує підсумовування Кехена-Бабушки і починає з цілого 0, тож `[-0.0].sum` дорівнює `0.0`.
- `Float#to_s` у Ruby використовує експоненційну форму починаючи з 1e15 (`1e15.to_s` дорівнює `1.0e+15`, `1e14.to_s` дорівнює
  `100000000000000.0`); `nil.inspect` усередині масивів дає `nil`.
- *фікстура* `\s` у Java охоплює лише ASCII; `split_whitespace` у Rust також ділить по U+00A0.
- Результати int-або-float у Python: `colorsys` зберігає int через `+`, `-` і `*`, тож точний порт
  обчислює з невеликим типом int-або-float замість `f64` (134 випадки, щойно int почали записуватися).
- `strtod("-")` у glibc нічого не перетворює і повертає `+0.0`, а не `-0.0`.

Оброблено в першому порті і підтверджено записаними випадками:

- `Integer.parseInt` у Java приймає будь-яку десяткову цифру Unicode (`١٢`, `２`) через `Character.digit`.
- `Double.toString` у Java (JDK 19+) друкує найкоротший десятковий запис, але не менше двох цифр:
  `4.9E-324`, тоді як найкоротша форма в Rust `5e-324`.
- `max(nan, 1, 2)` у Python дорівнює `nan` (перше значення перемагає, якщо наступне не виявиться більшим при порівнянні);
  `-0.0 % 1.0` дорівнює `0.0`.
- `toupper(-128)` у glibc дорівнює `128` (її таблиці приймають значення `char` зі знаком); `strtol` з основою 0
  читає `077` як вісімкове, а `0x` без шістнадцяткової цифри як `0`.

### Обмеження, які показали ці прогони

- **API C, що передають буфери.** Публічні функції aklomp/base64 приймають `char *out, size_t *outlen`
  або `struct base64_state *`. Міст C переносить лише скаляри і `const char *`, тож лишає
  їх усі в C, із зазначеною причиною. Підтримка шаблону з вихідним буфером буде наступним кроком для C.
- **Макроси C.** 43 з 51 файлу base64 визначають функції через макроси
  (`BASE64_ENC_FUNCTION(arch)`); парсер там повідомляє про помилки, і план позначає такі модулі
  як часткові. Інтринсики SIMD поки не позначаються як ризик.
- **Невизначена поведінка, яка не призводить до збою.** `ispunct(1000)` читає за межами таблиці glibc і
  повертає 1. Жоден порт не повинен цього копіювати; цей єдиний випадок прибрали з `cases.jsonl` вручну. Вбудованого
  способу позначити випадок як невизначений поки немає.
- **Динамічна типізація коштує коду.** Порт `shellwords` заново реалізує `to_s` і `inspect` з Ruby
  для чисел, nil, масивів і хешів, бо `shellescape` приймає що завгодно. Порт `colorsys`
  потребує числової ієрархії Python. Типізований порт коротший, але змінює поведінку для частини
  коду, що викликає; `diff` показує, для якого саме.
- **Фасади.** Прогони Java і C тестують справжню поведінку JDK і glibc, але через фасади,
  написані для прогону, а не через власний API бібліотеки.

## Як працює кожна мова

| | Запис | Diff | Міст | Shadow |
| --- | --- | --- | --- | --- |
| Go | згенерований драйвер, зібраний як окремий модуль з `replace` на оригінал | той самий драйвер поверх обгортки cgo | диспетчер JSON + пакет cgo з оригінальним API | пакет з оригінальним API, запускає обидва |
| Ruby | згенерований драйвер завантажує файли оригіналу | той самий драйвер завантажує обгортку Fiddle | диспетчер JSON + обгортка Fiddle, що визначає ті самі модулі | файл, який підключають через require після оригіналу: робить `prepend` обох |
| Java | драйвер на рефлексії, скомпільований з вихідним кодом оригіналу | той самий драйвер, скомпільований з класами-обгортками JNI | диспетчер JSON поверх JNI + класи-обгортки з оригінальними статичними методами | класи `<Class>Shadow` |
| Python | драйвер у процесі імпортує оригінал | той самий драйвер імпортує пакет PyO3 | PyO3 | модуль з оригінальним API |
| C | `cc -shared` оригіналу, виклик через ctypes, один fork на випадок | ctypes поверх `cdylib` на Rust | функції `extern "C"` з оригінальними іменами та заголовний файл | shadow `.c` з перейменуваннями через `-D`; можливість `shadow` крейта експортує лише імена `everything_rust_` |

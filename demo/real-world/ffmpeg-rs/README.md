# ffmpeg-rs

Portable C from [FFmpeg](https://ffmpeg.org)'s `libavutil` (tag `n7.1`, commit `b08d796`)
ported to Rust with everything-rust, one unit at a time, each proven against recordings of the
real ffmpeg functions and passing `everything-rust gate`. The case study is in
[`docs/real-world.md`](../../../docs/real-world.md#ffmpeg).
The same port is also its own repository: [erkamyaman/ffmpeg-rs-anything](https://github.com/erkamyaman/ffmpeg-rs-anything).

This is the portable C of libavutil, not ffmpeg's codecs. Rust does not beat hand-written
assembly, and a recording on one machine cannot vouch for code written for another CPU, so
everything target-specific stays in C (see "What stays in C" below).

## License

libavutil is LGPL-2.1-or-later. The Rust in this folder ports it, so it is LGPL-2.1-or-later too
(the license text is [`LICENSE`](LICENSE)); each `src/port.rs` names the file it ports and that
file's copyright holders. `adler32-rs` ports `adler32.c`, which ffmpeg took from zlib under the
zlib license; it keeps that license and notice. The wrappers in `wrappers/` call libavutil and
are LGPL-2.1-or-later as well. No ffmpeg source, test or recorded case is copied here: the
scripts clone ffmpeg and regenerate them.

226,447 recorded calls in all, every one matched by the Rust. The inputs (`scripts/inputs.py`)
are the vectors of ffmpeg's own `libavutil/tests/*.c` and FATE references (the CRC, MD5, SHA,
murmur3, base64, avstring and rational tests, regenerated by the script), plus seeded edge cases:
integer limits, invalid rounding modes, buffers one byte too small, strings with non-ASCII bytes,
every input split at many chunk sizes, and for `AVRational` `INT_MIN`/`INT_MAX` terms, zero and
negative denominators and NaN, infinities and subnormals for `av_d2q`. everything-rust adds its
own generated cases on top. 467 of the cases are ones where ffmpeg's own behavior is undefined
(a `NULL` it dereferences, an `av_strnstr` length past the end of the string, an invalid CRC id
it asserts on): they are recorded as the crash or out-of-bounds pointer they produced, and any
answer of the port passes them.

The six crates without the `oneshot-` prefix export libavutil's own functions with their C
signatures: link `target/release/lib<crate>.a` instead of the C object and callers do not change.
The hash and CRC APIs keep state across calls (`av_md5_init`, `av_md5_update`, `av_md5_final`
on an `AVMD5 *`) or hand out a table pointer (`av_crc_get_table`), and a per-call recording
cannot capture that. For those four, `wrappers/oneshot_*.c` are small one-shot C functions over
the real API (init, update in `chunk`-byte pieces, final); they are what was bridged and
recorded, and the Rust ports the whole algorithm behind them (context, buffering, padding,
tables). So for MD5, SHA, murmur3 and CRC the proof covers ffmpeg's algorithms and their
streaming, but the Rust does not yet export the `av_md5_*` API itself.

## Found along the way

`av_murmur3_update` (n7.1, and master as of 2026-11-20) returns early when a call exactly
completes a 16-byte block an earlier call had started, leaving the block unmixed. If that was the
last update, `av_murmur3_final` hashes it as the tail, so the digest depends on how the input
was split: the bytes 0 to 15 (default seed) in one call hash to `0be5b973...`, the same bytes
as 15 + 1 to `502abaf4...`. With more data after it the next call mixes the block and the digest is right.
`scripts/murmur3-split.c` shows it against `libavutil.a`. The port keeps the behavior, since the
bar is byte-identical output; the recordings caught it because the inputs feed every buffer at
several chunk sizes.

`av_q2intfloat` negates `q.num` and `q.den` with `*= -1`, which overflows for `INT_MIN`. The
recordings show what ffmpeg's build (clang 21, `-O3`) made of it: the sign test sees the wrapped
32-bit `num`, the division uses 2^31, and `x/0` returns `+inf` even for a negative `x` (clang
drops `num & 0x80000000` since `num` cannot be negative there without overflow). The port does
the same so the bits match; another compiler may answer differently for those inputs.

## What stays in C

- Everything under CPU-architecture folders (`x86/`, `aarch64/`, `arm/`, `ppc/`, `mips/`,
  `loongarch/`, `riscv/`): hand-written assembly, intrinsics and CPU feature detection. `analyze`
  marks those units `keep`. None of the ported units has assembly in n7.1, so the bench below is
  compiled C against compiled Rust.
- `av_parse_time`: it reads the clock and the local time zone, which a recording cannot pin.
- `av_strireplace` (returns memory it allocates with `AVBPrint`), `av_basename` (returns a
  static `"."` for an empty path), `av_get_token` (advances its own string and allocates) and
  `av_escape` (allocates its output).
- `av_find_nearest_q_idx` (reads a list through an `AVRational *`).
- `av_gcd_q`, `av_compare_ts`, `av_rescale_delta` and `av_add_stable`: they take `AVRational`
  by value too and the bridge carries them, but they are not ported yet.
- Contexts as an API (`av_md5_alloc` and friends), as above.

## Reproduce

Needs a C compiler, Python 3, Rust 1.88 or newer, git and make. From this folder:

```sh
scripts/prepare.sh   # clone ffmpeg n7.1 into work/, configure, build libavutil.a, assemble the tree
scripts/verify.sh    # per crate: record, build, diff, gate (prints the counts above)
scripts/bench.sh     # ffmpeg's libavutil.a against the ports, from one C program
```

`verify.sh` uses the everything-rust built from this repository (`cargo build --release` at the
root); the pointer support it needs is not in a release yet. The tree `prepare.sh` assembles
holds ffmpeg's `config.h`, libavutil's headers, the `.c` files the ported units link against and
the wrappers; recording compiles it with `CFLAGS="-I<tree> -DHAVE_AV_CONFIG_H"`, as ffmpeg's
build does.

## Bench

`scripts/bench.sh` links ffmpeg's own `libavutil.a` (built by its configure and make: Apple
clang 21, `-O3`) and one LTO staticlib of all the ports (rustc 1.100, built with the `shadow`
feature so it exports only `everything_rust_*` names) into one C program, and runs the same calls
on both until 200 ms pass, five times, printing the median. Apple M4 (10 cores), macOS, two
runs, load average 9 to 13 at the start (other builds were running), so read differences under
5% as noise. Hashes call ffmpeg's context API directly on a
preallocated context, the Rust one-shot function; above 1x the Rust is faster.

- **Even** (within 5% in both runs, or on different sides in the two): `av_adler32_update` to
  4 KiB, CRC-32, MD5, SHA-1 at 64 B, murmur3, `av_rescale_rnd`, `av_gcd`, `av_rescale_q`,
  `av_mul_q`, `av_d2q`, `av_q2intfloat`.
- **Rust faster**: `av_parse_video_size` (2.8x), `av_match_name` (2.2x), `av_stristr` (1.4x),
  `av_base64_encode` (1.1 to 1.3x), `av_adler32_update` at 1 MiB (1.02 to 1.07x) and
  `av_nearer_q` (1.03 to 1.06x).
- **C faster**: SHA-1 from 4 KiB (0.93x), SHA-256 (0.9x), `av_base64_decode` (0.86 to 0.97x),
  `av_reduce` (0.95x), `av_add_q` (0.92 to 0.95x), `av_strlcpy` (0.88 to 0.96x),
  `av_find_info_tag` (0.85x), `av_bessel_i0` (0.8x), `av_strstart` (0.78x), `av_strcasecmp`
  (0.7x) and `av_stristart` (0.6x).
- The string rows paid for the generated bridge: it turned each `const char *` into a slice,
  which runs `strlen` before the port starts, and `av_strcasecmp` on short words takes 1.2 ns in
  C, less than those `strlen` calls (the port ran at 0.23x). The bridge now lets a port take
  the string as `CChars`, read as it goes; `av_strcasecmp`, `av_strncasecmp` and `av_stristr`
  do, which took them to 0.68x and 1.4x. `av_strlcpy` and `av_find_info_tag` still take slices.
  `av_strstart` and `av_stristart` take `CChars` too, but a call costs ffmpeg about 1 ns, and
  turning the `const char **` into an offset and back on each call is a large share of that.
- A first port is not a fast one. MD5 first came out at 0.43x (it picked the round function with
  a `match` on every step); unrolled the way `md5.c` unrolls it, it matches C. A second pass did
  the same for the rest, each change replayed against the recordings again: SHA-1 and SHA-256
  unrolled with ffmpeg's rotating variable names instead of moving every variable each round
  (0.62x to 0.93x, 0.82x to 0.89x); CRC-32 reads its table as four `[u32; 256]`, so each lookup
  is one load as in C (0.84x to 1.0x); base64 decodes four characters at a time while none ends
  the input and encodes into 4-byte chunks (decode 0.6x to 0.9x, encode 0.85x to 1.1x);
  `av_stristr` checks the first character before comparing the rest.
  `av_bessel_i0` evaluated the same way as C's did not get faster.

So on this machine the ports are a correct drop-in at about C's speed: 18 of the 42 rows are even,
eight are faster, and the other 16 are slower by 3 to 40%, the slowest the 1 ns string calls.
